## Evidence envelope and verdict rules

Every run writes `evidence/<candidate>/<gate>/manifest.json` with: candidate revision and dirty-source digest; node/CLI/consensus/dependency revisions; tool versions and hashes; gate-definition hash and approval identity; command/seed/workload counts; start/end time; OS/CPU/clock/governor/memory; board silicon/flash/security mode and firmware hash where relevant; network genesis/parameters; baseline revision where compared; scope/exclusions; observed measurements; verdict (`pass`, `fail`, `inconclusive`, `unavailable`). Reports contain public keys, identities, periods, signature verification results and hashes only. Disposable secret seeds/states are generated at runtime and not retained in fixtures, logs or crash reports. Redact input artifacts containing generated secrets; retain a public reconstruction recipe/seed identifier only when it cannot disclose key material.

Zero executed cases, silently skipped hardware, timeout before required measurements, a successful process with missing report, wrong mode, mismatched revision or unapproved exclusion means **no valid reading**, not pass. A qualification runner must refuse mainnet/production fixtures for destructive scenarios, enforce explicit disposable-fixture authorization and check counts/coverage of required scenarios. Tests may not assert mocks/wiring/source text or pin incidental wording. Preserve behavioral regressions, not snapshots of accidental formatting.

### Candidate identity, freeze and bundle validation

An acceptance candidate has one frozen identity: revision plus a content digest of every repository-owned source (including tests, fuzz corpora, runners, validator, packaging, scripts and documentation), maintained dependency sources/patches, dependency lockfiles and resolved native plans, tool binaries/configuration, gate definition, approved applicability matrix and maintainer approval record. Record external oracle/dependency source hashes and packaged binary/firmware hashes in the same identity. A dirty worktree is not an escape: its complete source digest is part of the identity. Only a fixed, approved path allowlist for build outputs, generated evidence and disposable runtime fixtures may be excluded from the identity digest; no source, gate, approval, dependency or tool configuration may be excluded. Existing measurement-scope exclusions such as unmodified dependencies/generated code do not exclude those inputs from identity binding.

All runners, scenario inventories, semantic targets, sensitivity checks, evidence schemas, acceptance validator, traceability checks and packaging implementation must exist and pass their applicable implemented-scope checks **before candidate freeze**. Freeze also fixes commands, seeds/workload plans, exclusions and approval; generated build/evidence/runtime outputs are the only permitted subsequent writes. Final qualification is measurement-only: execute the frozen runners, build/package from frozen inputs and execute the already implemented validator. Do not implement/fix a runner, validator, package, documentation or application source during final measurement. Any changed frozen input creates a new candidate and requires reapproval where applicable and fresh readings for every applicable gate; no cross-candidate evidence reuse, even when a change appears unrelated. Baselines and sensitivity-probe records may be referenced as explicitly identified comparison/activation inputs, never substituted for candidate measurements.

Committed seed corpora and all frozen test inputs remain immutable. Copy seed corpora into preapproved excluded runtime work directories before fuzzing; corpus evolution, sanitized/minimized public failures and property-regression outputs go only into those directories/evidence, never back into frozen source. Mutation and sensitivity campaigns likewise use disposable runtime worktrees derived from the frozen candidate, with controlled probe/mutant differences recorded; these worktrees are measurement fixtures, not replacement candidate sources or an implicit source exclusion. Reports bind the original seed hashes, controlled probe/mutant diffs, actual commands and resulting sanitized corpus/output hashes to the unchanged clean candidate identity. Promoting a discovered regression or corpus input into committed source requires a new candidate and fresh measurements under the identity rules above.

Before freeze, test the validator with negative bundles that each independently fail closed: absent required gate/report/manifest; zero cases, empty corpus or empty mutant set; failed/inconclusive/unavailable gate; missing hardware reading; stale candidate/revision/source/tool/dependency/gate/approval hash; mixed-candidate reports; altered report content or packaged artifact hash; missing scenario/count/feature configuration; unapproved exclusion or a source path excluded from identity; missing traceability/approval; timeout/partial campaign despite subprocess exit zero. Also reject a bundle whose matrix marks an already implemented mandatory scope as future, or whose final-release matrix omits any full campaign. Exercise a complete valid disposable bundle as the positive control without representing synthetic evidence as a product reading. The final acceptance task only executes this frozen validator against real evidence and writes its verdict; it does not create or repair validation logic.

### Implemented evidence CLI and closed schema

T005 provides infrastructure validation, not a product acceptance reading. Use one explicitly built qualification executable throughout a candidate; its path/hash belongs in the approved tool inventory. The implemented entrypoints are:

```sh
"$XTASK" freeze --workspace "$WORKSPACE" --definition "$DEFINITION" --approval "$APPROVAL" --evidence "$EVIDENCE"
"$XTASK" gate run --candidate "$CANDIDATE" --gate G1
"$XTASK" acceptance --candidate "$CANDIDATE"
```

All variables here are absolute public file/directory paths. Definition and approval are reviewer-owned public metadata, not fabricated production bootstrap credentials. `freeze` refuses absent/mismatched approval and replacement of an existing candidate; `gate run` refuses replacement of any prior gate output. Gate definitions invoke `xtask gate NAME --evidence DIR` as a child of that approved orchestrator, not by choosing an implicit “latest” candidate. The CLI publishes each report exactly once. Missing runner/target/tool/calibration remains unavailable; subprocess success without a valid nonempty reading never passes.

Version-1 `Definition` is exactly `{version,increment,features,source_builds,tools,implemented_scopes,future_scopes,exclusions,inputs,artifacts,coverage_baselines,performance,gates}`. `increment` is setup/foundation/US1–US5/final; implemented/future scope prefixes must match the matrix. The fixed source-output exclusions are `.git`, `target`, `evidence`, never caller-expanded. `inputs` and `artifacts` map public names to paths and bind bytes separately even below an output namespace. External Git source revisions are recorded independently of source bytes. Coverage-baseline keys exactly cover G5 crate scenarios; null is allowed only for approved first measurement, never final. Performance specifies first-baseline establishment or a named frozen comparison input, never a report-selected baseline.

Each `SourceBuild` is exactly `{id,manifest_path,package,features,default_features,target,profile,all_targets,toolchain,rustflags}`. IDs exactly cover the frozen feature/configuration inventory. Real Rust workspaces require this inventory; file-only synthetic validator controls are not product build evidence. Freeze performs fresh locked/offline checks for every approved configuration, resolves the complete unfiltered dependency graph (including host-only build dependencies during cross compilation), verifies workspace package/feature and actual supported-target coverage, and binds compiler dependency records, included/generated sources, declared build-script watched inputs (including missing-path states), Cargo configuration search paths, public Cargo-home context, Rustup launcher and pinned toolchain binaries/libraries. Empty Cargo-home values fall back to HOME; relative values resolve against the child Cargo workspace consistently for discovery and execution. Host configurations compile all supported targets; feature-name union alone cannot satisfy a required-feature target. Undeclared arbitrary build-script I/O is not proven by rustc dependency records: source review and explicit public input declarations remain mandatory. Current-identity checks rehash the recorded closure without rerunning builds.

Each external `ToolRegistration` is `{program,version_args}`; tools record resolved physical path, SHA-256, version text and exact version arguments. Cargo plugins use their actual protocol, for example `["llvm-cov","--version"]`, not an assumed bare `--version`. The Linux session supervisor and signal utility are also bound. Each `Gate` is exactly `{id,program,args,scenarios,minimum_cases,hardware_required,budget_ms}`. Reports and manifests bind the full same-candidate identity, exact feature/scenario inventories, actual counts, terminal verdict and timing; each execution captures its own public host environment. JSON is size-bounded and rejects unknown schema fields and duplicate members, including nested measurement objects.

Every `gate run` owns a dedicated single-threaded Linux controller process, private `target/gate-runtime/<candidate>/<gate>` directory and newly supervised child session. Nested controllers use their own sessions and kernel child-subreaper adoption; descendants that change groups or lose their parents remain owned, are killed and reaped before report validation, and cannot keep writing after a completed cleanup. Tool groups stay within their controller's session. Runtime components derived from configuration labels are hashes, not raw labels that can contain path separators or Cargo-invalid colons. Owned runtime data is removed even when a child cannot run destructors. Completion or report validation past the approved budget is inconclusive, not a late pass. This is host process/evidence control, not physical board fault qualification.

### G8 power-cut occupancy matrix

Full capacity is a campaign requirement, not an invariant that forbids the lifecycle operation under test. Exercise all 32 registrations and full occupancy of 32 active plus 32 staged generations. Each trial records its initial occupancy, interrupted operation and permitted recovery outcome:

| Operation | Initial occupancy | Permitted successful recovery outcome |
|---|---|---|
| Generation/backup publication | 32 registrations, 32 active, 31 staged; target staged slot vacant | Target staged generation absent or durably published, according to commit state |
| Evolution | 32 registrations, 32 active, 32 staged | Correct committed period and cleanup state |
| Activation | 32 registrations, 32 active, 32 staged | Original context or committed replacement; committed activation consumes the target staged slot |
| Credential change | 32 registrations, 32 active, 32 staged | Correct old/new authorization outcome according to commit state |
| Deletion | 32 registrations, 32 active, 32 staged | Registration retained or durably deleted, with required cleanup and history preserved |

A previously acknowledged outcome remains binding in every row; permitted outcomes do not authorize rollback or fallback from a committed successor. Required vacancies and intentional lifecycle removals are not capacity failures. Unrelated pools retain their committed state, and acknowledged artifacts remain intact while within their specified retention lifecycle. Assess recovery before any workload restoration; restore occupancy only through supported lifecycle operations, without resetting replay history, rolling back state or importing private keys. ## G12 scope, interpretation and enforcement

The [pinned Clippy lint documentation](https://rust-lang.github.io/rust-clippy/rust-1.99.0/index.html#cognitive_complexity) explicitly warns that this lint does not calculate actual cognitive complexity; it retains the historical name and lives in the allow-by-default restriction group. Use it as the user's selected syntactic complexity guardrail. The fixed threshold is Clippy's documented default, made explicit for reproducibility, not a scientifically established comprehension boundary. Clippy reports functions exceeding the limit; an empty diagnostic list does not provide exact scores for every function.

Implementation must add the root `clippy.toml` with `cognitive-complexity-threshold = 25`. The gate runner sets `CLIPPY_CONF_DIR` to the absolute repository root for every invocation and records the file hash, rejecting missing/overridden configuration or flags that cap/silence lints. `-F clippy::cognitive_complexity` forbids local `allow`/`expect` overrides. Refactor for clearer responsibility boundaries, not merely to move branches into opaque helpers; human review remains necessary. Do not raise the threshold or exclude a difficult function after seeing a failure.

Run the host command in the G12 row for every supported host feature configuration. Also run `cargo clippy --locked -p kes-firmware --target thumbv8m.main-none-eabihf --release --message-format=json -- -D warnings -F clippy::cognitive_complexity` for each approved development/release firmware feature set separately; do not combine mutually exclusive security modes with `--all-features`. Check the maintained local KES adaptation using `cargo clippy --locked --manifest-path third-party/kes-summed-ed25519/Cargo.toml --all-targets --message-format=json -- -D warnings -F clippy::cognitive_complexity`, plus its firmware-compatible no_std configuration. Cargo does not automatically lint ordinary dependencies, so the explicit adaptation invocation is required. The approved matrix must additionally enumerate separately built fuzz/benchmark/test/qualification Rust targets so they are not omitted merely because they are outside default workspace members.

Scope includes project-owned Rust host/core/protocol/firmware code, tests and qualification tooling, and the maintained KES adaptation. Unmodified registry dependencies and mechanically generated code are exclusions recorded before evaluating the candidate, not counted as measured. Haskell native integration and prose/runbook comprehensibility remain outside Clippy's scope and continue to require independent review and operator trials. Capture every invocation's actual compiler-artifact/target identity, feature set and result; absence of relevant compiled targets cannot count as a valid reading.

Planning smoke evidence: the pinned installed Clippy was exercised in dependency-free disposable crates with the explicit threshold and enforcement flag. A function containing 24 independent conditional branches passed; adding a 25th branch failed with exit 101 and diagnostic `the function has a cognitive complexity of (26/25)`. The above-threshold fixture passed with `-D warnings` alone, confirming explicit enablement is necessary. Both `#[allow(clippy::cognitive_complexity)]` and `#[expect(clippy::cognitive_complexity)]` failed under `-F` with exit 101 and error E0453. Disposable fixtures were removed. These results prove host lint sensitivity and suppression rejection, not that the workspace/firmware passes G12. The definition is approved; activation still requires the complete actual configuration matrix and its sensitivity readings.

## Performance gates

**P0 — reproducible microbenchmarks (project gate, no invented sensor ID).** `cargo bench --locked -p kes-core --bench kes -- --save-baseline candidate`; qualification runner compares to an approved baseline revision stored with samples. Workloads: generate, all evolution boundaries including 31→32, sign/verify 0/256/4096-byte messages, codec and journal transforms. Criterion 0.8.2, 100 samples, 5-second warmup and 10-second measurement per case. Same CPU/toolchain, isolated cores, fixed governor, idle host and identical build flags. First correct implementation establishes the baseline; the current skeleton is not a performance baseline. After that, three independent runs: fail if the 95% confidence interval for runtime ratio is wholly above 1.05; pass only if wholly <=1.05; interval straddling threshold or environmental variance >5% is inconclusive and blocks comparison. Retain all samples, not only a favored rerun. Controlled inserted delay must produce a regression before activation. Budget 30 min; report allocations/peak buffers separately.

**P1 — physical admission-to-verified-result load (SO-006e).** `cargo run --locked -p xtask -- qualify load --fixture FILE --rounds 10000 --evidence evidence`. Measure actual USB/Pico at stock clock with qualified flash/security modes, not mock cryptography. A warm single-pool sample of10,000 requests must have >=99% <=100ms. In each of10,000 synchronized32-pool rounds, **every valid admitted request** must complete <=500ms including queueing, evolution/activation, transport and independent verification. Admission is acceptance by the host service, not later device dispatch: stamp the monotonic start and absolute deadline when the service accepts the request. Pending message bodies remain in bounded host queues; the device retains only its bounded admitted working buffers, never 32 full maximum-size messages. Run signing loads with 4096-byte messages as well as the specified smaller cases; a small-message-only run cannot satisfy P1. Host queue wait, device admission, reconnect/retry and verification consume the same original deadline, which is never reset. Separate workloads: all32 active+32 staged; one staged slot vacant with continuous background generation; aligned normal and midpoint transitions; activation bursts; saturation/flooded pool; oversize/overcapacity. Overload fails within500ms of service receipt; authorized status <=2s under saturation. Verify every signature; an invalid result is never a fast success. Report worst case and all misses, not averages alone. Require RAM/link/flash budgets in research R4 and record flash erase/program latency, stack high-water, wear projection, cold reconnect/recovery separately. Budget24h with all required rounds; a timeout before completion is inconclusive. Failure triggers an explicit requirement/hardware decision, never relaxed cleanup/capacity/deadlines.

The load fixture must enforce the protocol's exact queue/buffer model: one admitted sign per pool (32 total), plus one lifecycle and one status request per pool and one global management request retained on the host; round-robin host dispatch and cooperative generation; one device-dispatched operation globally. Device working buffers are one8192-byte nonsecure RX, one8192-byte secure request and one8192-byte response, with no extra4096-byte signing-message copy. Admission occurs at the daemon before USB waiting. The absolute deadline is also bounded by any earlier node slot deadline; dispatch transmits only the floored remaining budget, never a renewed budget. For node-backed loads the measured completion endpoint is validated signature completion at the node, including its verification, not daemon response arrival.

The public scenario names an absolute primary-workstation `kes-foundation-qualification` executable and a separate physical power-controller executable/endpoint; fixture creation never installs either. The qualification executable supports read-only `inspect --fixture FILE --output-format json-v1` and bounded `run --mode load|power-loss --fixture FILE --rounds|--cuts N --controlled-delay-ms N --output-format ndjson-v1`, with an optional named seeded defect only for sensitivity. It generates disposable secrets inside the protected runtime and writes public readings only. The xtask runner hashes the executable, rejects anything except stock-clock RP2350 A4-or-later/development mode/4-MiB fitted flash before a campaign, streams bounded strict NDJSON without replacing evidence, enforces the exact queue/timestamps/cut inventories and independently verifies every returned signature with both pinned native baselines. The physical controller must separately prove a ready physical endpoint. A2, a simulator, a missing executable/controller, malformed/empty records or self-reported summaries without complete per-operation readings are unavailable, never a pass.

## Acceptance ordering

There is no release-only escape from mandatory sensors. A missing, failed, unavailable or inconclusive required reading blocks acceptance. Under the approved A2 development-progression amendment, it does not block further implementation when the result is recorded as non-acceptance and the reading requires A4-or-later hardware. Maintainers still approve exact target/module/feature/scenario inventories before measurement and revalidate sensor applicability whenever architecture, dependencies, toolchain or supported behavior changes. An approval cannot waive a failed required reading, remove an implemented difficult path, reduce a threshold or label unimplemented behavior passed.
