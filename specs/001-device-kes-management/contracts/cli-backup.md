# Operator CLI, Cardano Compatibility and Backup Contract v1

Cardano compatibility baseline: unmodified **cardano-cli-11.4.0.0**, commit `25f4d7a6b243d80ed7d716cc91b9c51d9265ace6`. All commands added below belong to the planned Rust operator interface, not Cardano CLI. No cardano-cli source changes or fork are required: it remains the conventional key/certificate/query tool and an independent interoperability oracle. The existing `cardano-cli $era node key-gen-KES --verification-key-file ... --signing-key-file ...` remains unchanged and host-generated. No device failure invokes it as a fallback. The separate node/consensus external-signing integration still requires native changes.

## Commands and authority

`kes-forge` is the Rust operator binary, built from Cargo package `cardano-kes-forge`. Common device commands take `--connection FILE`, a configured pool connection containing the expected device/pool identity and socket/credential references, and optional `--json`. Management uses `--device-config FILE --authorization FILE` instead. Default production security policy rejects development/unverified devices. Only isolated test commands accept `--allow-development`; that flag cannot unlock release hardware.

## Versioned bootstrap files

These are planned production interfaces, not `xtask fixture` output requirements. All JSON schemas here are closed: require every named field, reject duplicate/unknown fields, null except explicitly allowed, unsupported versions, invalid UTF-8, trailing data and non-integer numbers. `version` is integer 1. Hex is lowercase without prefixes: identifiers 16 bytes/32 characters, pool IDs 28 bytes/56 characters, digests 32 bytes/64 characters. Integers are checked u64 unless bounded below. Every file is at most 16384 bytes; daemon configuration alone is at most 65536 bytes. Paths are non-empty UTF-8 strings, at most 4096 bytes, no NUL, resolved relative to the containing file (CLI paths relative to working directory). Names are 1–64 ASCII letters/digits/`-_.`; no implicit identity defaults. No permissive decoding or silent ignored fields.

### Standard authority and credential encodings

Ed25519 uses RFC 8032 pure Ed25519 (not Ed25519ph or Cardano extended cold keys). `publicKey` is canonical padded RFC 4648 base64 of the 44-byte RFC 8410 SubjectPublicKeyInfo DER (`302a300506032b6570032100` followed by 32 raw bytes); `privateKey` is base64 of the 48-byte RFC 8410 PKCS#8 DER (`302e020100300506032b657004220420` followed by the 32-byte seed). Algorithm OID parameters are absent. Reject other ASN.1 forms/algorithms, noncanonical base64, wrong lengths and private/public mismatches; derive and compare public keys before use. Use maintained reviewed Ed25519/PKCS#8 libraries, never a new signing algorithm or handwritten ASN.1 crypto. Device wire keys remain the specified raw 32-byte keys; decode these wrappers at the boundary.

`AuthorityPublicKey`: exactly `{version,algorithm,role,publicKey}`, with `algorithm="Ed25519"` and `role="management"` or `"provisioning-reviewer"`. `AuthorityPrivateKey`: same fields plus `privateKey`. `kes-forge authority key-create` generates keys with the workstation OS CSPRNG and refuses existing output paths. Management private files are usable only by `management sign`; reviewer private files only by attended `provision prepare/apply`. v1 authority private files are unencrypted PKCS#8 inside restricted JSON: keep them on offline encrypted storage under that role's custody; no passphrase environment/argv interface or claim of at-rest encryption by the file format.

`MachineCredentialPublic`: exactly `{version,algorithm,scope,deviceId,poolId,incarnationId,credentialEpoch,publicKey}`. `MachineCredential`: same fields plus `privateKey`. `algorithm="Ed25519"`; `scope` is `"pool"` or `"management"`. Pool scope requires pool/incarnation IDs; management scope requires both null. Credential epoch is u64, initially 0, thereafter exactly the authorized replacement epoch. These keys authenticate OPEN only; management transport is not management authorization. Creation accepts the expected public identity supplied by the ceremony, never pins an unauthenticated INFO response. `credential create` emits both files without overwrite and verifies their key/identity match.

All private files require regular non-symlink owner-owned files, mode `0600`, owner-only parent directories (`0700`), no group/other permissions and no untrusted writable ancestor. Daemon credential files/directories are owned by the daemon UID independently of client UIDs. Load with race-resistant no-follow checks; reject wrong ownership/mode rather than repair silently. Only the daemon loads credential bytes; node/operator client UIDs need read access only to public configurations/evidence, not credential paths or private directories. Public files are not secret but must be integrity-protected: trusted-owner-owned, no group/other writes or untrusted writable parent; public directories may be readable/searchable by intended clients through safe modes/ACLs, and need not be `0700`. Public-key transfers use authenticated out-of-band comparison of SHA-256 over the exact DER/public document bytes as appropriate, not first-use trust from USB. Authority key custody, cold signing, firmware signing and recovery are separate from the primary, even if an operator holds multiple roles.

Authority and machine credential creation must establish locked, non-dumpable zeroizing memory and disable core dumps before generating a seed or serializing private PKCS#8 JSON; fail if required protection is unavailable. Validate derived public identity before publication. Publish the intended private output as an unnamed `O_TMPFILE` inode in the protected destination directory, mode `0600`, then fsync/linkat-no-replace/directory-fsync under the same no-symlink/no-overwrite rules as secret-safe recovery publication below. No named private scratch file, stdout, environment value, shell pipeline or secret diagnostic is permitted; fail without an unsafe fallback on unsupported filesystems, and wipe transient seed/DER/base64/JSON buffers on every exit. Public/private pair publication is not an all-files atomic transaction: report success only after both files are durable; a partial publication is an explicit publication failure, never permission to overwrite either output or use an unverified pair.

### Public identity, configuration and enrollment

`DeviceIdentity`: exactly `{version,deviceId,identityPublicKey,hpkePublicKey,managementPublicKey,managementTransportPublicKey,credentialEpoch,bootKeyFingerprint,hardwarePolicyDigest,firmwareDigest,securityVersion,provisioningRecordFile,provisioningManifestFile,reviewerPublicKeyFile}`. The identity and management keys are Ed25519 SPKI encodings above; transport key too. `hpkePublicKey` is exactly 32 raw X25519 bytes as 64 lowercase hex, boot fingerprint/policy/image hashes are 32-byte hex. Management and reviewer keys originate from their separate authenticated public handoffs. The identity/HPKE keys are fresh device-generated production keys; trusted attended readback and signed provisioning record bind them to `deviceId`, not an untrusted host key-generation command. `hardwarePolicyDigest` equals the record's `policyDigest`. Provisioning file references identify the completed reviewer-signed record and exact signed manifest defined in security.md; their public dependencies remain available by their manifest-relative paths. Online INFO must match this pin and record; no connection constructor learns trust automatically.

`DeviceConfig`: exactly `{version,socketPath,deviceId,deviceIdentityFile,connectionName,credentialFile,credentialEpoch,securityPolicy}`. The credential is management-transport scope; initial identity/key/epoch match the provisioning record. Subsequent key/epoch changes must match the durably authorized current management-transport policy under the pinned device, not require rewriting historical provisioning evidence. `securityPolicy` is `"release-required"` for production or `"isolated-development"` only for disposable fixtures. This is the local management connection, not a USB path or offline authority.

`PoolConnection`: exactly `{version,socketPath,deviceId,deviceIdentityFile,poolId,incarnationId,networkBinding,connectionName,credentialFile,securityPolicy}`. Preserve these node-contract names. Credential scope/IDs/epoch must match enrollment and daemon reconciliation; no private material in node bulk JSON. `networkBinding` is exactly `{networkMagic,shelleyGenesisDigest,slotsPerKesPeriod,maxKesEvolutions}`: network magic u32, SHA-256 of exact Shelley genesis file bytes, positive u64 slots per period, evolutions 1–64. Do not substitute the node's differently encoded genesis hash. Security policy has the DeviceConfig values.

`DaemonConfig`: exactly `{version,socketPath,usbDevice,deviceConfigFile,poolConnectionFiles,allowedPeerUids}`. `usbDevice` is an explicit stable USB selector (1–256 printable ASCII bytes), resolved against the pinned device rather than trusted as its identity. `poolConnectionFiles` is an array of 0–32 distinct pool files. `allowedPeerUids` is an array of 1–64 exact `{uid,connections}` objects: uid is a unique u32; connections is an array of 1–33 distinct registered connectionName strings, with no wildcards or implicit access. Authorize each request by its SO_PEERCRED UID and explicit connection mapping, not socket access alone. All referenced sockets/device IDs must agree; connection names and pool IDs are unique. Mapping is static at startup; adding a pool file or changing UID permissions requires daemon restart, not a new authority bypass. Daemon starts with zero pool files and the provisioned management transport, explicitly mapping its service UID to that management connection. Later map intended node/operator UIDs only to their pool connections. `kes-forged --config FILE` validates all files before creating its protected Unix socket with access modes/ACLs for configured clients, authenticates pinned evidence when connected and exposes management prepare/apply; missing live USB means unavailable, not trust bootstrap. Never place authority or recipient private keys in this configuration.

`EnrollmentPayload`: exactly `{version,deviceId,poolId,incarnationId,coldVerificationKey,networkBinding,machinePublicKey,credentialEpoch,recipientPublicKey,recipientId}`. Cold VK is raw 32-byte lowercase hex decoded from the conventional Cardano cold verification envelope; pool ID is its BLAKE2b-224. Machine key is the Ed25519 public encoding above, epoch initially 0, recipient raw X25519/ID from the recipient public JSON. `enrollment-create` checks MachineCredentialPublic bindings, derives genesis digest and `slotsPerKESPeriod`/`maxKESEvolutions` from the supplied Shelley genesis, and refuses supplied network-magic mismatch. Incarnation is a fresh OS-CSPRNG 16-byte identifier chosen for this enrollment and never recycled. Expected directory revision and next management sequence come from authenticated `management prepare`, not guessed values in this payload. Offline signing displays and verifies all bindings against approved public inputs; no enrollment implicitly accepts a new boot root or firmware image.

Public documents/configuration may be assembled by an operator/editor from these exact schemas; no generator or fixture is required. `deviceId` is the fresh 16-byte identity assigned in the attended ceremony; request/incarnation IDs can be generated with `openssl rand -hex 16` on the responsible host. Genesis, cold VK, approved signed firmware/partition manifest and ROM boot-key fingerprint come from independently authenticated existing network/cold/release workflows. Firmware ECDSA signing and conventional cold/VRF generation remain in their existing tools, never converted into Ed25519 management keys. A missing approved image, hardware-specific recipe or trust pin blocks bootstrap rather than triggering automatic firmware/OTP enrollment.

Routine lifecycle commands obtain expected revision and certificate digest through the configured authenticated connection. They may reconcile a concurrent revision and ask the operator to retry a conflict, but may not overwrite a changed active generation or create an extra staged generation. Their request ID is generated once and persisted in a restricted public operation record before dispatch. CLI device generation requires explicit request ID/generation number for crash-safe batch use. A lost response is resolved using the same identity. `--json` changes output formatting, not authority.

`kes-forge key-gen-KES` calls the local daemon protocol directly; it does not wrap or extend cardano-cli. It validates returned VK, artifact signature/bindings and device commitment before publishing output. If one output was published before a host crash, retry accepts it only when its validated content matches this exact operation; an unrelated existing file is an error. Success is reported only after all outputs and the public completion manifest are durable. It is not an all-files atomic filesystem transaction.

## Standard Cardano artifacts

`kes.vkey`: JSON text envelope with `type="KesVerificationKey_ed25519_kes_2^6"`, human description and `cborHex` encoding a 32-byte CBOR bytestring (`5820` followed by key bytes). `kes.skey`: `type="KesSigningKey_ed25519_kes_2^6"`, description and `cborHex` encoding the 608-byte initial state (`590260` followed by state bytes). The internal Rust period suffix is NOT copied into this file. JSON spacing/description are not cryptographic identity; compare parsed bytes/type. The independent CLI 11.4 and node 11.1.3 oracles must both accept these files.

`node.cert`: unchanged `NodeOperationalCertificate` envelope encoding `(OCert, cold verification key)`. Issuance remains `cardano-cli $era node issue-op-cert` on the existing cold-key workstation. The certificate signs hot VK/counter/start period, not a network identifier. Network authorization is an additional enrolled binding, never a fictional certificate field.

## Immutable encrypted backup encoding

Binary `.kes-backup`: eight-byte ASCII magic `KESBKP01`, then deterministic CBOR map, <=2048 bytes total. Map fields:

| Field | Encoding |
|---|---|
| `version` | unsigned integer 1 |
| `kem`, `kdf`, `aead` | unsigned integers 32, 1, 3 |
| `device`, `incarnation`, `generation` | 16-byte bytestrings |
| `pool` | 28-byte bytestring |
| `generation_number` | u64 |
| `verification_key`, `recipient_public_key` | 32-byte bytestrings |
| `recipient_id` | SHA-256 of raw recipient public key, 32 bytes |
| `period` | unsigned integer 0, only initial-state backups permitted |
| `encapsulation` | 32-byte HPKE encapsulated key |
| `ciphertext` | exactly 608 encrypted bytes plus 16-byte AEAD tag |
| `device_signature` | 64-byte Ed25519 signature |

Define `header` as deterministic CBOR of fields from `version` through `period`. HPKE `info` is ASCII `cardano-kes-forge/backup/v1` concatenated with `header`; AAD is magic concatenated with `header`. Encrypt exactly the raw 608-byte initial state. Sign `"cardano-kes-forge/backup-signature/v1" || magic || deterministic-CBOR(map without device_signature)` with the pinned device identity. Reject unknown versions/suites, missing/duplicate/extra fields, malformed/noncanonical values and trailing bytes. HPKE base encryption alone does not authenticate the device; validate this signature against the externally trusted identity file before recovery. Artifact metadata must match caller expectations and supplied conventional VK; after decryption, derive VK independently and compare again.

There is one artifact per generation, produced and committed before any generation output is advertised. No replacement recipient, password change or period transition modifies those bytes. Retain/archive old recipient keys as long as their artifacts are needed. Retired artifacts may be reclaimed from device storage after rotation; the host warns before reclamation, not after data loss.

## Recipient files and passphrases

Public file: JSON `{ "version":1, "algorithm":"X25519", "publicKey":"<64 lowercase hex>", "recipientId":"<64 lowercase hex>" }`. Private file: magic `KESRCP01` followed by deterministic CBOR containing `version=1`, `kdf="argon2id"`, `argon_version=19`, `memory_kib=65536`, `iterations=3`, `parallelism=4`, `salt` (16 bytes), `aead="XChaCha20Poly1305"`, `nonce` (24 bytes), `public_key` (32 bytes), `recipient_id` (32 bytes), and `ciphertext` (32 private bytes plus 16-byte tag). The entire public header including magic is AAD. Enforce exact supported KDF parameters before allocating; do not permit a hostile file to request unbounded RAM/work. A later KDF change requires an explicit format-version decision.

Passphrases come from an echo-disabled controlling terminal, never argv, environment variables, stdout, logs or a daemon. Creation/password replacement confirms a non-empty passphrase; recommend a long unique passphrase. Byte interpretation is UTF-8 without normalization; confirmation compares exact bytes. Recovery prompts once for the existing password; password change requires successful old-key decryption first. Empty input cancels without mutation. Reject noninteractive invocation rather than falling back to an environment variable. Machine automation of password entry is not part of v1.

Create keypairs with the backup OS CSPRNG. Verify protected-file decryption and derived public identity in memory before publication. Password change generates fresh salt/nonce, decrypts/re-encrypts the same private key, verifies the new protected file, fsyncs it, atomically replaces the old encrypted file and fsyncs the directory. Only encrypted staging files may be named on disk. An interruption preserves a valid old or new protected file. It cannot revoke a copied old file/password pair.

## Secret-safe output publication

Recovery runs only on the designated separate backup/recovery workstation, selected through operator procedure and installation/OS access control; a CLI cannot cryptographically prove what physical host it runs on. Production primary packaging does not install recipient recovery/private-key workflows and must not possess recipient secrets. An operator can violate custody by manually copying secrets; the platform makes no impossible host-location guarantee against that action.

Before publishing plaintext, verify artifact structure/signature, expected identities, recipient key, AEAD tag and derived VK. Use locked, non-dumpable zeroizing memory; fail if required memory protection cannot be established. Disable core dumps and avoid swap exposure. Never log raw inputs. Restrict output parent directory to its owner and reject symlinks/path traversal through untrusted parents.

Publish only a complete owner-readable/writable (`0600`) intended output inode. On supported Linux local filesystems use an unnamed `O_TMPFILE` inode in the protected destination directory, write only the validated final key, fsync, and `linkat` without replacement followed by directory fsync. This inode is the intended output, not an incidental plaintext scratch file; no named plaintext temporary, shell pipeline or serialized secret intermediate is permitted. If anonymous/no-replace publication is unsupported, fail explicitly rather than using an unsafe fallback. Existing output path always fails for recovery. On write/validation failure no pathname is linked; release/zeroize unlocked material on every exit. A failure after linking/fsync uncertainty may leave a complete validated output, never a partial key; report publication uncertainty without overwriting it on retry.

The deliberate development output follows identical protection rules but includes current period and device/generation identity in a distinct `KESDEV01` format. It is not a node-loadable period-zero backup and is never accepted by release firmware/import paths. It uses only disposable runtime-generated keys and is excluded from version control and ordinary diagnostic bundles.

## Machine output and errors

Successful `--json` output is one JSON object on stdout: `version`, `operation`, `requestId`, `deviceId`, `poolId` (nullable), `generationId` (nullable), `revision` (nullable), `result`. Public status includes `securityMode` (`development`, `release-unprovisioned`, `release-ready`), `releaseEvidenceVerified`, health, active/staged descriptors, certificate start, confirmed relative period, backup availability and blocking reason. It also includes host-only `observation`, `ready`, `remainingValidityPeriods` and `latency` below. Never expose credential bytes or private material. Passphrase prompts and diagnostics use stderr/terminal, not machine stdout.

`observation` is exactly `{state,observationMaxAgeMs,confirmedAgeMs,nodePeriodAgeMs,confirmedObservedAt,nodePeriodObservedAt,context,historical}`. `observationMaxAgeMs=30000` is fixed, not configurable. Ages are nonnegative integer host-monotonic elapsed milliseconds or null when no observation exists; timestamps are RFC 3339 UTC display metadata or null. Context is null or `{deviceId,bootNonce,sessionId,poolId,incarnationId,networkBinding,generationId,certificateDigest,revision}` using protocol identity lengths. Historical is null or the last validated committed public descriptor, explicitly not current readiness. State is `"fresh"` only if both confirmed state and authorized operational node-period observation match the current context, each age is <30000ms, and no mutation is unresolved. At either age **>=30000ms**, report `"stale"` if the connection/context remains usable. Absent observations, disconnect, reboot, session replacement, daemon restart, invalid context or unresolved mutation mean `"unavailable"` immediately. Preserve facts only as historical; no stale/mismatched period produces remaining validity. Device STATUS and operator activation inputs cannot refresh the node period; requested mutation is not confirmation. Active rotation invalidates the old join; staging alone does not. `remainingValidityPeriods` is a nonnegative integer only for the fresh joined active context, otherwise null. `ready` is a nullable boolean: null unless the join is fresh/current; for a fresh join it is true only if reconciled identities, security, certificate lifetime and health permit service, otherwise false. Unknown readiness is never encoded as false.

`latency` is exactly the fixed eight-operation object defined in [device protocol](device-protocol.md#host-observation-freshness-and-operational-latency): `GENERATE`, `GET_BACKUP`, `CERTIFY`, `ACTIVATE`, `SCHEDULE`, `EVOLVE`, `SIGN`, `OBSERVE_PERIOD`. Each entry is exactly `{state,sample}`. State is `"fresh"` for sample age <30000ms, `"stale"` at >=30000ms, `"unavailable"` with sample null before completion/after daemon restart or session replacement. A non-null sample is exactly `{operation,requestId,durationMs,outcome,code,observedAt,ageMs,context}`: operation matches its key; request ID is 16-byte lowercase hex; duration is nonnegative milliseconds rounded up; outcome is `"success"` or `"error"`; code is a stable protocol result/error; observedAt is UTC RFC 3339; ageMs is host-monotonic elapsed integer milliseconds; context has the observation context identity fields, with generation/digest/revision nullable when none exists yet. Internal monotonic completion time is never a portable wall-clock timestamp.

Retain only the last completed sample per pool/operation in daemon RAM (maximum 32×8). Measure admission before host queueing through validated response (including daemon signature verification) or terminal failure/deadline; the native node still independently verifies under its original deadline. GENERATE measures the initial validated IN_PROGRESS acknowledgement, not the full asynchronous job. Status/polling/completion manifests cannot turn that sample into a full-generation performance claim. A terminal timeout/error is recorded even if later reconciliation finds a committed mutation. Admission rejection before timing begins is a command error, not a completed sample. Disconnect invalidates readiness but a newly terminal transport-failure sample may still display error latency until reset/expiry. STATUS, OP_STATUS and diagnostic reads never create/overwrite/reset samples or refresh their ages. Invalid authenticated replies never refresh committed observations. These are host-only operator diagnostics; preserve native KES telemetry names, cadence, historical mappings, aggregation and error sentinels unchanged. The fixed TTL is a proposed v1 design setting, not measured hardware performance.

Management-scope device/directory status has no pool observation or per-pool measurements: `poolId`, `generationId`, `observation`, `ready`, `remainingValidityPeriods` and `latency` are null. It may report verified device security/health and directory facts independently; those do not manufacture a pool readiness join or latency sample.

Operator binary exit codes, including `kes-forge key-gen-KES`: 0 completed; 2 usage/static configuration; 3 authentication/security; 4 conflict/not-yet-valid/expiry/capacity; 5 unavailable/deadline/entropy; 6 damaged state or integrity failure; 7 filesystem/publication failure. Nonzero machine output is a bounded JSON error with stable `code`, scope and public context. Existing cardano-cli commands retain their native exit-code and output conventions unchanged.

Wrong password/recipient, modified artifact, missing archive/recipient key, output collision, unavailable device and lost acknowledgement are distinct explicit errors. No error claims to erase external copies. Primary and recovered backup evolve independently; stop one producer before starting the other. Password/recipient changes cannot undo leaked KES secrets; suspected compromise requires a fresh generation and matching externally issued certificate.
