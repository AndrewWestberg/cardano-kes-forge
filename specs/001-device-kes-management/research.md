# Phase 0 Research: Device-Protected KES Management

Research date: 2026-10-23. Scope: [spec.md](spec.md), FR-001–FR-032, SC-001–SC-012. Findings below are source observations and design decisions, not implementation or hardware qualification results. Three read-only research agents were dispatched for node integration, CLI/crypto, and hardware security; all failed before research because their provider credential had expired. Research was completed directly. Software Observatory MCP calls succeeded.

## R1. Compatibility baselines and native integration

**Decision:** Move the sole proposed cardano-cli extension, device KES generation, into the Rust operator executable as `kes-forge key-gen-KES`, retaining existing device-generation flags without an era/`node` prefix, old command alias or host-generation fallback. No cardano-cli source modifications or fork are needed. Require **unmodified cardano-cli-11.4.0.0**, commit `25f4d7a6b243d80ed7d716cc91b9c51d9265ace6`, for external certificate issuance, conventional key/query operations and the independent compatibility oracle. Use cardano-node 11.1.3, upstream commit `938cba990357ae7c4b7f95c8f75dd9d31174bbeb`, as the independent node compatibility baseline; node/consensus modifications remain required in their supplied native checkouts without resetting local changes. Build the unmodified CLI oracle and node in separate Cabal dependency graphs; communicate through versioned bytes/files, not a shared Haskell ABI.

**Rationale and observations:**

- The [CLI 11.4.0.0 release](https://github.com/IntersectMBO/cardano-cli/releases/tag/cardano-cli-11.4.0.0) exists; its local tag resolves to the commit above. Its manifest requires `cardano-api ^>=11.9` and `cardano-crypto-class ^>=2.6`. Index states are Hackage `2026-09-02T14:05:07Z` and CHaP `2026-10-13T14:57:01Z`.
- Select [cardano-api 11.9.0.0](https://chap.intersectmbo.org/package/cardano-api-11.9.0.0/), source `dccda6c57080a0dbc944dba21f37e387a9fd7e0c`; [cardano-keys 11.0.0.0](https://chap.intersectmbo.org/package/cardano-keys-11.0.0.0/), source `0250d3608196116e3ab935a783267026c1ec090f`, Cabal revision r2; and [cardano-crypto-class 2.6.0.0](https://chap.intersectmbo.org/package/cardano-crypto-class-2.6.0.0/), source `12168e4b32b44d30dd401010ccd969accaf2add7`, for the CLI-side interoperability oracle. **Alternatives considered:** Extending or adding a cardano-cli device-generation command is superseded: the existing Rust operator surface can own device generation without maintaining a CLI fork, while preserving the same device-only behavior, output lifecycle and recovery boundary. Node/consensus patches are still necessary for native device signing and cannot be eliminated by this CLI decision. Reusing the prototype's CLI 11.2.3.0 is rejected by the user's explicit baseline. Upgrading node and consensus to CLI's dependency graph would add unrelated migration scope. Treating the local CLI fork as the release oracle would hide compatibility drift. Retain separate unmodified upstream CLI/node oracles and patched node/consensus workspace runs, with native package solver plans archived before implementation acceptance.

## R2. Sum6KES and Rust dependency strategy

**Decision:** Use the existing Apache-2.0 `kes-summed-ed25519` 0.2.1 implementation as the starting cryptographic dependency, with a separately reviewed, pinned Cargo path patch for no_std support, bounded buffers, secret-safe errors and cooperative generation/public-cache support. Do not invent Ed25519, BLAKE2b, HPKE, AEAD or a new KES construction. Do not copy any Pico HSM application code. Compare the adapted library against both unmodified Rust 0.2.1 and independently built Cardano release oracles; the latter are authoritative for interoperability.

**Rationale:** The [published crate](https://docs.rs/kes-summed-ed25519/0.2.1/kes_summed_ed25519/) already implements Sum6KES. Its [manifest](https://github.com/input-output-hk/kes/blob/master/Cargo.toml) and [library](https://github.com/input-output-hk/kes/blob/master/src/lib.rs) do not provide a no_std feature and enable std defaults in dependencies. It cannot be represented as a drop-in firmware dependency. Its buffer API and fixed-depth tree make a narrow adaptation preferable to an unrelated implementation. The upstream warning that it is unaudited remains applicable; adaptation and dependency adoption require independent security review. Preserve upstream attribution and record the precise source checksum and patch digest in Cargo.lock/release evidence.

The governing composition is [MMM section 3.1](https://eprint.iacr.org/2001/034), concretized by Cardano's pinned `Cardano.Crypto.KES.Sum` and `Single` implementations. Use Sum6KES with standard Ed25519 and BLAKE2b-256: 64 relative periods (0–63), 32-byte public key, 608-byte conventional signing state, 448-byte signature. Never substitute CompactSum6KES. The Rust library's period metadata is not part of the 608-byte Cardano key file. Test exact serialization and every transition against the two Haskell oracles; size arithmetic alone is not evidence.

A complete public tree has 127 32-byte nodes (4064 bytes). Cache only public tree material to avoid repeated subtree work at midpoint transitions. Generate incrementally with one global bounded generation workspace; keep secrets and expanded signing caches in fixed buffers, zeroizing on replacement/error. Any optimization must preserve byte-for-byte oracle behavior and all period-boundary checks. Review unsafe operations only at hardware/locked-memory boundaries, with invariants and safe-alternative rationale.

**Alternatives considered:** Direct dependency without adaptation fails bare-metal compilation. A new SumKES implementation adds avoidable cryptographic maintenance. HSM C port violates the greenfield requirement. A recursive implementation with unbounded foreground key generation risks starving admitted signers.

## R3. Hardware, transport and runtime

**Decision:** Target stock-clock Pico 2 RP2350 A4 or later, Arm Cortex-M33 secure execution, `thumbv8m.main-none-eabihf`; do not use RISC-V in release. Use Rust 1.99.1/edition 2024, `embassy-rp =0.10.0` with RP235xA support, an Embassy USB vendor-specific bulk interface, and a Linux daemon `kes-forged` owning the USB handle. Node and Rust `kes-forge` operator clients use restricted Unix-domain sockets; unmodified cardano-cli does not connect to this service. Cargo package/project, node-source discriminator and protocol/crypto domains remain `cardano-kes-forge`; executable naming does not rename those identities or directories. No PC/SC, HSM APDUs, PKCS#11, TCP listener or new remote management service.

**Rationale:** [Embassy RP 0.10.0](https://docs.rs/embassy-rp/0.10.0/embassy_rp/) supports RP235x, USB, flash and secure image definitions. Separate transport and no_std domain logic permits host fault testing without pretending to emulate hardware security. Firmware signing/OTP packaging uses picotool 2.3.1 as a build/provisioning tool, not HSM application linkage. Firmware has fixed queues, one admitted sign attempt per pool, round-robin service, bounded management/status work, and interruptible generation steps. Flash programming/erase coordination must include both cores and RAM-resident critical code; the HAL alone is not a security policy.

The [RP2350 security white paper](https://pip-assets.raspberrypi.com/categories/1214-rp2350/documents/RP-009377-WP-1-Understanding%20RP2350_s%20security%20features.pdf), release 1, documents A4 ROM vulnerability fixes, irreversible OTP policies and why a mode label is not proof. Capability inventory and verification are in [security.md](contracts/security.md). Device identity is pinned during a trusted attended ceremony; USB serial and self-supplied public keys are not roots of trust.

For entropy, use only health-checked RP2350 TRNG samples for credited entropy; reject samples on hardware health errors and fail closed after a bounded acquisition window. The inspected [Embassy TRNG reference](https://github.com/embassy-rs/embassy/blob/main/embassy-rp/src/trng.rs) uses sample count 200, one inverter, all health checks enabled, and warns about low sample counts while sleeping. Do not assume its current main implementation is present unchanged in 0.10.0. Pin the reviewed register sequence in the hardware adaptation, return typed `ENTROPY_FAILURE` rather than an infinite retry/panic, and qualify its settings on supported silicon. No SDK xoroshiro/time/USB data fallback. A cryptographic DRBG seeded from this source supplies session randomness and seeds; it must be a reviewed maintained dependency with published vectors, not a custom generator. Select `rand_chacha` 0.9.0 ChaCha20Rng, seeded with 256 health-checked bits, reseed before each generation and session establishment; deterministic seeding exists only in host test APIs.

**Alternatives considered:** Prototype CCID imposes unrelated protocol/framework baggage. Multiple USB owners create routing/reconnect races. A per-pool process is insufficient for mixed bulk acceptance. General async work stealing is unnecessary; bounded round-robin is easier to qualify. USB product VID/PID assignment remains a distribution prerequisite: development uses only legitimately authorized IDs, never an invented production allocation.

## R4. Persistence, capacity and timing risk

**Decision:** Use a small explicit authenticated double-bank flash journal per pool plus a double-bank device directory. Preserve immutable encrypted backups/public tree objects separately. Commit successor, erase/read-verify predecessor, clear superseded RAM, then durably mark cleanup complete before acknowledging evolution or serving a signature in the new period. No filesystem copy-on-write or wear-leveling layer may retain undeclared obsolete secret copies.

**Rationale:** Power loss after successor commit but before erase must recover the successor and finish cleanup, not select an older period. A damaged committed successor must quarantine affected state, not silently fall back. [data-model.md](data-model.md) defines marker ordering and replay invariants. Use XChaCha20-Poly1305 authenticated snapshots with fresh 24-byte nonces and versioned AAD; root keys are device-specific OTP-derived keys. Nonce generation failure blocks mutations. Per-pool revisions are not OTP counters: ordinary lifecycle does not consume scarce hardware rollback fuses.

Proposed flash budget (design ceilings, not measured usage): 64 KiB boot/partition area + two 1 MiB signed firmware slots + 16 KiB directory + 32 × 32 KiB pool regions = 3152 KiB, leaving 944 KiB of a detected 4 MiB board. A pool region allocates two 4 KiB secret banks, two 8 KiB public/artifact objects and 8 KiB reserved. Every secret snapshot must fit within 3584 bytes including authentication overhead, leaving separate 256-byte COMMIT and CLEAN pages. No format may spill into another pool. Keep certificate/replay tombstones in the directory after deletion; bounded directory exhaustion fails enrollment rather than losing history. Directory compaction may remove a tombstone only with explicit management authorization binding a new incarnation and preserved high-water marks.

The original active-cache allocation alone costs `32 × (608 + 4064 + 64) = 151552` bytes. Keeping another 32×4096-byte message bodies on the device would exceed the 256-KiB ceiling before other state. **Decision:** retain service-admitted bodies on the daemon, dispatch one device operation at a time, and parse exact signing bytes in the single secure frame copy. The 32-pool admission guarantee remains service-wide; host queue time remains inside the original deadline. Staged trees/secrets and cold certificate/registration data are loaded into shared workspace on demand, not duplicated for every pool.

Proposed peak KES-owned SRAM ceilings (bytes, not measured usage):

| Resident allocation | Bytes |
|---|---:|
| 32 active secret/public-tree/expanded-key caches | 151552 |
| One nonsecure receive + one secure request + one response frame, 8192 each | 24576 |
| 33 session records, at most 256 each | 8448 |
| 32 hot pool records, at most 256 each; cold metadata remains authenticated in flash | 8192 |
| Dispatch/operation metadata | 4096 |
| Shared crypto/generation/staged-load workspace, including transient HPKE | 32768 |
| Shared journal candidate/authentication workspace | 8192 |
| Combined KES stack allowance across both cores | 16384 |
| Unallocated KES margin | 7936 |
| **Total ceiling** | **262144** |

No allocation is hidden outside this ledger merely by placing it in nonsecure RAM. Account alignment, DMA descriptors and interrupt stack peaks within the listed ceilings; the complete firmware's non-KES USB/runtime allocation is reported separately and still counts against 520 KiB physical SRAM. Assert fixed buffer capacities at compile time, record linker/static sizes and measured stack/workspace high-water marks, and require at least 32 KiB measured free SRAM after complete firmware and peak workload. Exceeding any proposed component ceiling requires an explicitly reviewed rebalance inside the unchanged total, not an unchecked spill or threshold increase.

Host storage is separately bounded: at most 32 signing, 32 lifecycle, 32 status and one management frame, each <=8192 bytes (794624 bytes of queued payload capacity), plus at most 64 socket-peer receive frames of 8192 bytes (524288 bytes), and fixed metadata/session/diagnostic records. A queue slot includes its in-flight request until terminal completion; each peer has one incomplete frame with 2-second expiry and excess peers are refused without allocating another buffer. Exact body bytes stay on the host until dispatch; no prehash substitution, double secure-body copy or per-pool device frame cache. Public cache acceleration remains part of the dependency adaptation, not proof that the current crate meets timing. Firmware code-size and all 64 retained objects must also fit actual link/flash measurements.

**Critical feasibility gate:** 32 obsolete-sector erases plus cryptography/USB at an aligned period transition may exceed 500 ms. Measure this first on stock hardware, including 31→32, flash stalls, 32 simultaneous maximum-4096-byte service-admitted signing messages and independent verification. Record admission/dispatch/completion timestamps separately; no reset when a body leaves the host queue. Exercise all-active/all-staged and separate background-generation peak memory layouts. Do not assume asynchronous APIs make synchronous erase latency disappear. Failure blocks this 32-pool design; capacity, erasure ordering and deadlines may change only with an explicit user-approved requirement/hardware decision. Identify the fitted flash and its minimum endurance; project wear from supported network periods and routine rotation, not an invented generic endurance number.

**Alternatives considered:** Append-only secret logs retain obsolete material. Erasing before commit loses acknowledged state. Acknowledging before cleanup violates forward-erasure semantics. Battery/secure-element additions or lowered capacity are not authorized. Physical flash substitution/invasive extraction is outside scope, but host-accessible rollback and ordinary power loss are not.

## R5. Backup and password lifecycle

**Decision:** Enroll an X25519 recipient public key, generated on a separate recovery workstation. Encrypt each generation's period-zero state once using RFC 9180 HPKE base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, ChaCha20-Poly1305 (IDs 0x0020/0x0001/0x0003), plus a device Ed25519 signature over the complete canonical artifact. Use `hpke =0.13.0` in-place APIs; require vectors and review because its documentation explicitly disclaims an audit. A device signature supplies origin authentication that HPKE base mode alone does not.

Protect the recipient private-key file with Argon2id v1.3 (64 MiB, t=3, p=4, 16-byte random salt, 32-byte output) and XChaCha20-Poly1305 with a fresh 24-byte nonce. Use RustCrypto `argon2 =0.5.3`, `chacha20poly1305 =0.10.1`, `ed25519-dalek =2.2.0`, `x25519-dalek =2.0.1`, `sha2 =0.10.9`, `hkdf =0.12.4`, and `zeroize =1.8.2` as initial exact direct pins, subject to license/advisory/target review before adoption. Firmware defaults disable std/alloc where supported; recipient KDF is host-only. Lock transitive versions/checksums through Cargo.lock. No package is accepted merely because a version is listed here.

**Rationale:** [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180) defines interoperable public-key encryption; [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106) supplies Argon2id guidance. This avoids delivering passwords or private recipient material to the primary/Pico. A versioned file format records parameters and authenticates identity fields; [cli-backup.md](contracts/cli-backup.md) defines exact publication/error behavior. Password change rewraps the same private key with fresh salt/nonce. Recipient replacement affects future generations only. There is no password-reset bypass.

**Scripts investigated:** `scripts/cardano/mainnet/04c_genKESKeys.sh:90–174` invokes software generation, captures plaintext into shell variables, optionally displays the password, and prints the signing file. `01_protectKey.sh:79–89` displays the input secret; `00_common.sh:2949–2977` uses symmetric GPG and passes a password argument; line 23 advertises a password environment variable. These are workflow references only. None is a runtime dependency, compatibility format, or approved secret-handling pattern for this platform.

**Alternatives considered:** Password on Pico prevents unattended rotation and widens custody. GPG-in-JSON is not recipient-public-key export. A permanently unlocked recovery service adds unnecessary exposure. Renaming encrypted files to `kes.skey` misrepresents node compatibility.

## R6. Per-pool node integration and telemetry

**Decision:** Add a dedicated native external-signing credential variant; do not repurpose kes-agent's key-delivery protocol. Preserve legacy bulk tuples exactly and add discriminated version-1 object entries for file/device sources. Validate source exclusivity per credential, duplicate pool identity and static bindings before startup; do not make valid file-backed entries depend on USB availability. Details and telemetry inventory: [node-integration.md](contracts/node-integration.md).

**Rationale:** `Protocol/Shelley.hs:267–273` accepts triples of embedded text envelopes, not triples of file paths. `HotKey` currently returns a signature without a recoverable failure result, while `NodeKernel` calls block forging after eligibility checks. Changing only the initial eligibility check cannot handle a disconnect during signing. Introduce typed signing/forging failure through affected constructors/callers and catch it at the actual forging boundary; never use a fake key or signature. Capture certificate/generation/period as an immutable attempt context; activation racing it must either follow completion or make the attempt fail. Hot rotation reloads the committed device descriptor, not a stale host certificate.

`KESInfo.hs:60–162` computes `current = certificate_start + confirmed_relative_evolution` and `remaining = max(0, expiry-current)`. Existing error metrics set current/remaining to **0**, not -1. Machine log field names `endPeriod` and `evolution` have surprising historical values; preserve them. The CLI lifetime query uses chain tip, genesis and era/time context without a signing key. Observations reuse normal signing-state metadata; telemetry never advances the device.

**Alternatives considered:** Process-wide source choice, homogeneous-only bulk operation, or a new dashboard fail explicit requirements. Treating a requested period as confirmed produces false readiness. Giving every gauge a new pool label changes existing aggregation semantics and is outside scope.

## R7. Quality-tooling selection and evidence

**Decision:** Adopt the nine inspected Software Observatory sensors and project-specific gates in [quality-gates.md](contracts/quality-gates.md), including the user's requested **G12 `clippy::cognitive_complexity`** guardrail with an explicit threshold of 25 and `-F clippy::cognitive_complexity` enforcement. Full sensor entries were read through MCP, not selected from keyword scores alone. Tools: Cargo/rustc 1.99.1 and its Clippy component; proptest 1.11.0; cargo-mutants 27.0.0; cargo-llvm-cov 0.9.1; cargo-fuzz 0.13.1 with nightly-2026-10-22; Criterion 0.8.2; hardware/public-interface qualification runner built at the candidate revision. Exact direct pins are proposed; tool activation requires demonstrated defect/regression detection and maintainer approval before implementation gates are treated as active.

**Rationale:** Behavior, generated state transitions, test sensitivity, execution coverage, malformed input, independent crypto compatibility, fault survival, real saturation and a syntactic complexity guardrail answer different questions. The catalog coverage call returned no unknown IDs and five represented families; uncovered families remain invariants, change, architecture, evolution and comprehension. A subsequent MCP lookup and enumeration of comprehension sensors found no cognitive-complexity entry, so G12 is explicitly project-specific, not a fabricated catalog mapping. [Clippy's documentation](https://rust-lang.github.io/rust-clippy/rust-1.99.0/index.html#cognitive_complexity) warns that this allow-by-default restriction lint does not measure actual human comprehension; `-D warnings` alone does not activate it. G12 addresses Rust code-complexity risk without replacing independent security review or SC-001/SC-006 operator trials. Its threshold/enforcement was smoke-checked on the pinned installed toolchain with a passing boundary case and a failing `(26/25)` diagnostic; full workspace/firmware qualification remains pending. Property/fault invariants, native regression runs and dependency review similarly do not fabricate catalog readings. Evolution/history metrics have no meaningful greenfield baseline; A/B exposure/shadow production signing is inappropriate because it can authorize duplicate forging. Formal proof is not claimed.

**Alternatives considered:** A passing Cargo test exit, coverage percentage, benchmark mean, or an MCP consultation alone cannot establish correctness. Treating `cognitive_complexity` as actual human-comprehension evidence, or relying on the existing `-D warnings` command to enable an allow-by-default lint, would overstate coverage. Use the requested lint explicitly and retain human review/operator trials; do not substitute unrelated lints silently. Do not invent an Observatory ID for either G12 or Criterion microbenchmarks. Physical load testing maps to SO-006e; deterministic microbenchmark regression remains a separate project gate.
