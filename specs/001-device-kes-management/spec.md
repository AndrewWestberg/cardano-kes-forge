# Feature Specification: Device-Protected KES Management

**Feature Branch**: `001-device-kes-management`

**Created**: 2026-10-23

**Status**: Draft — CLI generation, backup location, and recipient-password lifecycle clarified

**Input**: Create cardano-kes-forge for secure KES generation, management, evolution, and signing on a Raspberry Pi Pico 2. Updated scope: a greenfield Rust project, not an HSM port; one device serves multiple pools on one machine; cardano-node gains a third configurable KES option while retaining file-based KES and kes-agent; device-generated keys support conventional backup producers; state survives power-down and the node may supply periods and evolution instructions.

- Q: How should operators request device-backed KES generation? → A: The user supplied this requirement directly: extend `cardano-cli $era node key-gen-KES` or add a dedicated cardano-cli command to optionally generate the initial KES key on the Pico 2, export its verification key for external cold-key operational-certificate issuance, and provide the matching signing key for a conventional backup producer. Retaining the initial backup key removes the deployment-wide forward-security guarantee even though the legacy node still evolves KES state for signing.
- Q: Where may the device-backed key-generation workflow write the plaintext `kes.skey` file? → A: Only on the authorized backup/recovery system (Option A). The user also requested investigation of password-protected export and the existing operator scripts before deciding how passwords are provisioned, protected, changed, and used for decryption.
- Q: Should the password protect a recipient private key on the backup system, or directly protect exports through a secret provisioned to the Pico? → A: Protect the recipient private key only on the authorized backup/recovery system (Option A). Enroll only its public key on the Pico. Generation needs no password; recovery unlocks the recipient private key locally. Changing its password does not change the recipient keypair, device configuration, or existing encrypted KES artifacts. Replacing the recipient keypair requires management authorization and affects future generations only.

## User Scenarios & Testing *(mandatory)*

Stake-pool operators need one Pico 2 to protect the primary signing state of multiple pools while their cardano-node processes share the same host. KES (key-evolving signatures) advances through numbered validity periods. Each pool has independent credentials, keys, certificates, and lifecycle state. The device performs evolution and signing; it does not send signing keys to nodes using the cardano-kes-forge option.

A controlled backup exception permits an encrypted copy of each newly generated initial signing state to be recovered as conventional Cardano key files on a separate authorized backup system. Device-local erasure and forward-only evolution do not erase exported backups or prevent those backups from deriving earlier or later signing states. An operational certificate authorizes a KES verification key for a pool and starting period; the existing external cold-key workflow continues to issue it.

### User Story 1 - Generate Pool Keys and Compatible Backups (Priority: P1)

An operator provisions the device, registers pools and their authorized backup recipients, then selects device-backed generation through cardano-cli for each pool. The Pico 2 generates the initial KES key locally. The workflow supplies a standard public verification key for external certificate issuance and an encrypted initial-state signing-key export; only the authorized backup/recovery system writes the decrypted conventional signing-key file.

**Why this priority**: On-device key creation must protect the primary host without preventing existing conventional backup producers from operating.

**Independent Test**: Exercise the unchanged software-generation command and the device-backed cardano-cli workflow for two registered pools. Obtain their public verification keys and encrypted signing-key exports, recover each export on the authorized backup/recovery system, and verify that conventional Cardano tooling derives the matching public key and accepts the recovered signing-key file.

**Acceptance Scenarios**:

1. **Given** a provisioned device and an authorized pool registration, **When** a generation completes durably, **Then** it exposes a stable pool and generation identifier, standard `kes.vkey`, and one encrypted backup of the matching initial signing state; neither the primary host nor a node using cardano-kes-forge receives plaintext signing secrets.
2. **Given** an encrypted backup and its authorized recipient on a separate trusted system, **When** recovery completes, **Then** the resulting conventional `kes.skey` derives the supplied verification key and can be used with the same externally issued operational certificate as the device generation.
3. **Given** a retained generation-time artifact, **When** it is retrieved repeatedly or after evolution and restart, **Then** the same artifact is returned; ordinary evolution creates no fresh backup and changing the authorized recipient applies only to future generations.
4. **Given** a wrong recipient, altered artifact, unauthorized export request, or pool-mismatched credential, **When** access or recovery is attempted, **Then** it fails without revealing plaintext or changing protected state. Plaintext device export and private-key import are unsupported.
5. **Given** insufficient secure randomness, power loss, or a lost generation response, **When** the caller retries or inspects status, **Then** no incomplete generation is advertised as usable and an already committed generation is identified rather than silently replaced by a newly generated key.
6. **Given** existing use of `cardano-cli $era node key-gen-KES --verification-key-file /tmp/core.kes.vkey --signing-key-file /tmp/core.kes.skey`, **When** device generation is not selected, **Then** existing software-generation behavior remains unchanged. When device generation is explicitly selected through an extension or dedicated command, the initial key is generated on the selected Pico 2 for the intended pool; failure never silently falls back to host generation.
7. **Given** a device-generated verification key and encrypted signing-key export, **When** the operator completes the documented recovery workflow on the authorized backup/recovery system, **Then** it writes a conventional `kes.skey` matching `kes.vkey`. The verification key is available for external cold-key certificate issuance without backup decryption; an encrypted artifact alone is not described as a file that an unmodified backup node can load.
8. **Given** an authorized backup/recovery system, **When** the operator sets up a backup recipient before first device-backed generation, **Then** the supported workflow creates a recipient keypair there, protects its private key with a confirmed non-empty passphrase, and makes only its public key available for management-authorized pool enrollment. Neither the primary nor the Pico receives the recipient private key or passphrase.
9. **Given** an enrolled recipient public key and an unattended primary, **When** a new KES generation is requested, **Then** the device produces the encrypted signing-key export without a password prompt or access to the recipient private key.
10. **Given** an encrypted KES export, the protected recipient private key, and the correct passphrase on the authorized backup/recovery system, **When** the supported recovery command runs, **Then** it verifies the artifact's integrity, expected device/pool/generation, and matching verification key before publishing a restricted-permission conventional `kes.skey`. It does not print secrets or modify the encrypted input. A wrong password, wrong key, altered artifact, or existing output path produces an explicit failure without publishing partial plaintext or overwriting an existing key.
11. **Given** a usable protected recipient private key, **When** its password is changed through the supported local workflow, **Then** the keypair identity remains unchanged and existing artifacts can still be recovered with the newly protected private-key file, with no device update. An interrupted password change preserves a usable old or new protected file rather than destroying the only recoverable key.
12. **Given** a management-authorized replacement recipient keypair, **When** it is enrolled, **Then** future KES generations are encrypted to the new recipient while old artifacts still require the old recipient private key. Losing all usable copies of that key or its unlocking credentials makes those artifacts unrecoverable; changing a password or recipient does not revoke copied secrets.

### User Story 2 - Select Device Signing for Multiple Pools (Priority: P1)

An operator configures cardano-node to use file-based KES, kes-agent, or cardano-kes-forge for each applicable pool credential. Multiple pools on the same primary machine concurrently use one device, with requests routed only to their own authorized pool state.

**Why this priority**: The product must work as a real third node option without breaking either existing option or requiring one device per pool.

**Independent Test**: Run actual node configurations using each of the three options. Exercise concurrent device-backed pools on one machine, independently validate their blocks, and separately run a conventional backup producer using a recovered key and matching certificate.

**Acceptance Scenarios**:

1. **Given** a valid node configuration selecting exactly one KES option for a pool credential, **When** the node starts, **Then** it uses that option. Existing file-based and kes-agent configurations retain their behavior; ambiguous source selections are rejected. Both individual and bulk pool-credential loading support the new option.
2. **Given** multiple authorized pools sharing the device, **When** their nodes request signatures concurrently, **Then** every successful result matches the correct pool, generation, certificate, exact signing content, and period and is independently verified before block submission. No plaintext KES state is transferred to a node using cardano-kes-forge.
3. **Given** a credential for one pool, malformed input, a wrong certificate or network, or a stale generation, **When** signing or evolution targets another pool or mismatched context, **Then** the request fails without changing another pool's state or submitting an invalid block.
4. **Given** device absence at startup or disconnection during operation, **When** a device-backed pool needs to sign, **Then** that attempt fails explicitly while node synchronization continues. Reconnection restores later valid signing without node restart, manual runtime unlocking, or automatic switching to another KES option.
5. **Given** excessive requests or a pool-local fault, **When** healthy pools continue requesting service, **Then** excess work receives bounded failures and one pool does not monopolize the device or select another pool's key. A device-wide hardware failure may affect every attached pool and is reported as such.
6. **Given** an exported conventional key and its certificate, **When** the operator stops the primary producer and starts the backup through the existing file-based option, **Then** independent validation accepts its blocks without requiring cardano-kes-forge on the backup. Failover scheduling and prevention of simultaneous primary/backup forging remain the operator's responsibility.

### User Story 3 - Resume and Evolve Safely after Power-Down (Priority: P1)

An operator powers down or disconnects the device and later resumes service without regenerating keys, importing a backup, or losing committed pool state. Each node supplies its current period or evolution request, and the device catches up safely before signing.

**Why this priority**: Durable state and unattended resumption are necessary for both KES correctness and ordinary operation; routine power loss must not be treated as a reason to abandon a valid key.

**Independent Test**: Populate multiple pools with independent periods and staged generations, power-cycle the device, reconnect their nodes, advance across skipped periods, and verify signatures and retained public metadata. Interrupt lifecycle operations at their persistence boundaries.

**Acceptance Scenarios**:

1. **Given** successfully committed pool registrations, authorizations, generations, certificates, backup artifacts, and periods, **When** the device is powered off and on, **Then** those records remain available and authorized service resumes unattended after safe recovery, without creating new identities or resetting periods.
2. **Given** a node-supplied later period within a generation's valid lifetime, **When** evolution is requested, **Then** the device performs and durably commits forward evolution before signing in that period. The public verification key, generation identifier, certificate, and generation-time backup stay unchanged.
3. **Given** a repeated current-period request or an earlier period, **When** it is processed, **Then** the current-period request does not advance again and the earlier-period request is rejected, including after reboot. Ordinary signing does not itself create a new generation or require a persistent lifecycle mutation.
4. **Given** power loss during an ordinary state-changing operation within supported storage behavior, **When** recovery runs, **Then** it automatically recovers a consistent committed state, never earlier than the last acknowledged state, and finishes required obsolete-state cleanup before serving. A durable but unacknowledged successor is reconciled rather than repeated. Irrecoverable corruption is separately reported and blocks the affected state; it is not silently reinitialized or counted as successful power-loss recovery.
5. **Given** a device left unpowered across several periods, **When** a node reconnects with the current period, **Then** the device catches up before signing if the generation is still valid, or explicitly expires it and awaits an authorized replacement. It makes no claim to evolve or erase secrets while unpowered.
6. **Given** concurrent generation, evolution, activation, or delayed responses for the same pool, **When** operations complete, **Then** none restores an older period, resurrects a retired device generation, overwrites newer committed state, or associates a response with a different request.

### User Story 4 - Inspect and Rotate Pools Independently (Priority: P2)

An operator inspects each pool, generates a replacement and matching backup, obtains a certificate externally, and activates or schedules the replacement without stopping other pools or restarting their nodes.

**Why this priority**: Multi-pool operation is useful only if normal replacement and management do not disrupt unrelated block production.

**Independent Test**: Populate all supported pool registrations, retain active and staged generations simultaneously, rotate one pool while others sign, and exercise a scheduled activation after restarting the device and host-side service.

**Acceptance Scenarios**:

1. **Given** a provisioned device, **When** an operator requests status, **Then** it reports device health and per-pool identity, authorization, active and staged generations, certificate start, current relative period, remaining validity, backup availability, and signing-blocking conditions without exposing secrets. Remaining-validity information identifies stale or missing node-period observations rather than claiming current readiness.
2. **Given** an active pool, **When** one replacement is generated and staged, **Then** its public key and encrypted backup are available before certificate issuance while that pool and the others remain able to sign. A second staged generation conflicts rather than silently replacing the first.
3. **Given** a staged generation, **When** a certificate for another pool, key, network context, or unacceptable certificate counter is supplied, **Then** certification or activation fails without replacing a valid active generation. Certificate issuance and cold secrets remain outside this platform.
4. **Given** a valid certified staged generation, **When** an authorized lifecycle operation activates it at an eligible node-supplied period, **Then** the device commits the replacement, removes its superseded active secret, and subsequent signing uses the matching new certificate without node restart. A raced old-generation request completes before activation or fails explicitly; it cannot mix old and new signing contexts.
5. **Given** an operator-approved future activation, **When** the node later reports an eligible period, **Then** activation proceeds without another human action. Restarting device, node, or host-side service preserves or reconciles that intent and the committed public certificate; device state is not rolled back to match a stale host file.
6. **Given** an expired active generation with no ready replacement, **When** signing is requested, **Then** it fails explicitly rather than generating a new key or certificate automatically. A later valid certified replacement can restore service.

### User Story 5 - Revoke Pool Access and Recover Service (Priority: P2)

An operator replaces or revokes a pool's machine credential, deletes a pool, or retires the device through a separate management authority. Existing exported keys support backup producers if the device fails; replacement hardware receives newly generated keys rather than imported historical state.

**Why this priority**: Pool isolation and recovery must remain meaningful despite the intentional backup exception and shared hardware.

**Independent Test**: Revoke one pool's credential while another signs, restart the device, attempt replay and cross-pool operations, and retire a test registration. Rehearse an operator-managed backup interval and replacement-device provisioning.

**Acceptance Scenarios**:

1. **Given** a registered pool, **When** management-authorized credential replacement or revocation commits, **Then** the old credential cannot access that pool after restart, while unrelated pools remain available.
2. **Given** a normal pool machine credential, **When** it attempts to enroll or delete pools, replace credentials, redirect future backups, or authorize firmware changes without management approval, **Then** the device rejects it. Replayed or altered management authorizations also fail without changing state.
3. **Given** an explicitly management-authorized pool deletion or device retirement, **When** success is reported, **Then** the affected device-held secrets and authorizations stay unusable after restart. The operation does not claim to erase previously exported artifacts or remotely invalidate existing backup producers.
4. **Given** a failed or lost device, **When** the operator uses an available generation-time backup through the existing procedure, **Then** a conventional producer can operate for that key's remaining valid lifetime without the original device. The procedure requires avoiding concurrent forging and explains that unreachable devices and external copies cannot be remotely erased.
5. **Given** replacement hardware, **When** the operator restores the device-backed service, **Then** it generates fresh keys and uses new matching certificates through the normal external workflow; there is no device private-key import or rollback recovery path. Missing backup artifacts or recipient keys are explicit limits, not recoverable through a hidden bypass.

### Edge Cases

- All 32 pools have active and staged generations; a 33rd registration or second staged generation is rejected without overwrite. Sparse registrations retain their stable identities, and deletion/re-enrollment does not silently reset replay or certificate history.
- Multiple pools reach a KES boundary simultaneously, including the Sum6KES midpoint transition. Generating or rotating one pool must not starve others or undo evolution committed during background work.
- The node requests an earlier period, repeats the current period, skips periods, supplies an inconsistent network context, or reaches the first invalid period. KES periods are not epochs or a hardcoded number of days.
- Power fails during generation, backup publication, evolution, activation, credential changes, or deletion. No partial artifact/key pair is advertised as complete, and acknowledged state never regresses.
- A response is lost after a durable change, a request is duplicated, or a late result arrives after cancellation. Status reconciliation identifies the committed result without creating another generation or accepting a stale signature.
- A backup is altered, addressed to the wrong recipient, lost, or retrieved after its generation is no longer retained. Retrieval of a retained artifact is repeatable; operators must archive it before rotation reclaims it. Recipient changes do not rewrite existing backups.
- A recipient password change is interrupted, a wrong password is entered, or the recovery output path already exists. Preserve a recoverable protected recipient key, fail without partial plaintext output, and never expose secrets in diagnostics.
- The operator changes the password protecting a recipient private key but retains the same keypair. Existing KES artifacts and device enrollment remain unchanged. A copied old protected private-key file is still unlockable with its old password; password changes are not revocation.
- Primary and backup use the same key and certificate. Their evolution is independent; no ordinary evolution export or continuous secret synchronization is needed. Shared certificates do not prevent double forging.
- A compromised authorized primary can request signatures, advance its authorized pools prematurely, or deny service. It must not extract plaintext keys, redirect backup recipients without management authority, or bypass firmware and storage protections. Pool isolation does not protect credentials already stolen from the same host.
- A pool-local damaged record blocks that pool rather than selecting another pool's state. Device-wide configuration damage, entropy failure, or hardware loss may block all pools and must be reported distinctly.
- File-based or kes-agent mode remains explicitly selectable, but failure of a configured cardano-kes-forge source never silently selects either as a fallback.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: One Pico 2 MUST serve up to 32 independent registered pools concurrently on one primary machine, including 32 active and 32 staged generations at once. Each pool MUST retain stable identity and independent credentials, certificates, periods, and lifecycle state. Capacity conflicts MUST reject without overwrite. Acceptance: Stories 2 and 4; full-capacity edge cases; SC-003.
- **FR-002**: Fresh Cardano-compatible Sum6KES generations MUST be created on the device using security-appropriate randomness. Public keys and matching encrypted backups MUST become available only after durable successful generation; retries MUST resolve the same committed generation. Acceptance: Story 1, scenarios 1 and 5.
- **FR-003**: The device MUST permit only encrypted generation-time backup export to a previously management-authorized recipient. It MUST NOT offer plaintext device export, private-key import, evolved-state export, or retention of extra initial plaintext solely for later export. Primary-host outputs and diagnostics MUST disclose no plaintext KES secret, seed, or recipient private key. Acceptance: Story 1, scenarios 1–4; SC-004.
- **FR-004**: Initial provisioning MUST be operator-authorized; normal boot, reconnection, evolution, signing, and pre-authorized rotation MUST operate unattended without runtime PINs or button confirmation. Per-pool machine authority MUST be distinct from the offline management authority required for enrollment, credential or recipient changes, deletion, and firmware authorization. Management authorization MUST resist replay across restart. Acceptance: Stories 2, 4, and 5.
- **FR-005**: The platform MUST supply conventional `kes.vkey` and recipient-side recovery of conventional `kes.skey`, matching the same generation and operational certificate. Plaintext `kes.skey` MUST be written only on the authorized backup/recovery system. The primary MUST NOT handle recovery plaintext or any password/private key sufficient to decrypt its retained backup artifacts. Backup producers MUST remain operable through existing file-based KES without this platform as a runtime dependency. Acceptance: Story 1, scenarios 1–2 and 7; Story 2, scenario 6; SC-007.
- **FR-006**: Each certified generation MUST bind the registered pool identity, KES verification key, valid cold-signed operational certificate, start period, acceptable certificate counter, and registered network KES parameters. Invalid bindings MUST fail without damaging a valid active generation. Cold signing keys and certificate issuance MUST remain external. Acceptance: Story 4, scenarios 3–4.
- **FR-007**: cardano-node MUST expose cardano-kes-forge as a mutually exclusive third KES source alongside existing file-based KES and kes-agent, preserving the existing modes and supporting individual and bulk credential configurations. In the new mode, the device MUST perform evolution and signing directly; node and host integration MUST hold no plaintext device KES state. Acceptance: Story 2, scenarios 1–2 and 6; SC-002 and SC-007.
- **FR-008**: Requests and responses MUST bind the intended device, pool, generation, exact signing content, and period. Node integration MUST verify the returned signature against the selected signing context before submitting a block and reject stale, malformed, mismatched, or invalid results. Acceptance: Story 2, scenarios 2–3; Story 3, scenario 6.
- **FR-009**: Authenticated node-supplied periods and evolution requests MUST drive forward-only device evolution within the registered network's permitted lifetime. Repeated current-period requests MUST be harmless, earlier periods MUST fail, and evolution MUST preserve the generation's public key, certificate, and backup artifact. Obsolete device signing states MUST be erased before acknowledging advancement or returning a new-period signature. This guarantee does not extend to exported copies. Acceptance: Story 3, scenarios 2–3 and 5.
- **FR-010**: Successfully committed registrations, authorizations, generations, certificates, periods, and retained encrypted backups MUST survive power-down. Ordinary interrupted lifecycle operations within supported storage behavior MUST recover automatically to a consistent state no earlier than the last acknowledged state. Irrecoverable corruption MUST block affected use explicitly, without silent reinitialization. Acceptance: Story 3, scenarios 1 and 4; SC-005.
- **FR-011**: The platform MUST derive validity from certificate start and registered network KES parameters, refuse out-of-lifetime signing, erase expired device signing state on committed expiry, and preserve public expiry metadata and any staged replacement. It MUST NOT hardcode a rotation interval or rely on a device clock to evolve while unpowered. Acceptance: Story 3, scenario 5; Story 4, scenario 6.
- **FR-012**: Operators MUST obtain the per-device and per-pool status in Story 4, scenario 1, plus bounded operational error and latency information sufficient to distinguish unauthorized requests, capacity pressure, expiry, disconnection, recovery, and damaged state. Stale period observations and unavailable measurements MUST be labeled rather than presented as current or zero. Logs and status MUST contain no signing secrets, credentials, or backup plaintext. Acceptance: Story 4, scenario 1; SC-001 and SC-004.
- **FR-013**: Each pool MUST support one staged replacement beside its active generation, including its own backup and certificate handoff, without disrupting other pools. Authorized immediate or scheduled activation MUST use an eligible node-supplied period, retire the old device generation, reconcile interrupted certificate publication, and enable hot rotation without node restart. Acceptance: Story 4, scenarios 2–5; SC-006.
- **FR-014**: Failure or absence of a configured device signer MUST fail the affected forging attempt explicitly without invalid block submission, node termination, or automatic KES-source fallback. Safe reconnection MUST restore later valid signing unattended while node synchronization continues. Separately configured conventional backup producers remain supported. Acceptance: Story 2, scenarios 4 and 6.
- **FR-015**: Input and workload limits MUST be bounded and declared. Scheduling MUST prevent one authorized pool or background generation from starving other admitted pools; overload and expired requests MUST fail within the signing-attempt deadline, and late results MUST not be reused. Acceptance: Story 2, scenario 5; SC-003.
- **FR-016**: Management-authorized revocation, credential replacement, pool deletion, and device retirement MUST persist across restart and affect only their authorized scope. Successful device erasure MUST NOT imply revocation or erasure of external backups. Acceptance: Story 5, scenarios 1–3.
- **FR-017**: Operator procedures MUST cover provisioning, pool enrollment, all three node options, generation and encrypted backup retrieval, recipient-side recovery, certificate handoff, unattended period handling, rotation, revocation, deletion, and device replacement. They MUST explain external backup custody, independent backup evolution, simultaneous-forging risk, and the limits of lost-device recovery. Acceptance: Stories 1–5; SC-001, SC-006, and SC-007.
- **FR-018**: The release MUST demonstrate protection against unauthorized host use, cross-pool access, plaintext secret extraction through exposed interfaces, recipient redirection, unauthorized firmware replacement/downgrade, and command-driven restoration of obsolete device state. Invasive physical attacks are excluded under Assumptions. The permitted encrypted backup is an explicit exception to pool-wide non-exportability and forward erasure, not evidence that plaintext extraction is acceptable. Acceptance: security edge cases; SC-004.
- **FR-019**: Generation, all Sum6KES period transitions, signatures, verification-key and signing-key files, and operational-certificate handling MUST be compatible with the declared Cardano release. Evidence MUST use governing specifications and authoritative vectors or an independent release-compatible implementation, including midpoint, final-period, network-lifetime, and wrong-certificate cases. Existing file-based and kes-agent behavior MUST retain regression evidence. Acceptance: Stories 1–3; SC-002 and SC-007.
- **FR-020**: A generation's encrypted backup MUST be created once with the fresh key and remain identically retrievable while that generation is retained as staged, active, or current expired state. Evolution MUST NOT re-export current secrets. Recipient changes MUST affect future generations only; the operator MUST be told to archive artifacts before reclamation. Acceptance: Story 1, scenario 3; backup edge cases.
- **FR-021**: Pool-local authorization, lifecycle, and recoverable connection failures MUST not select, roll back, or erase another pool's state. Shared hardware or device-wide security faults MUST be clearly distinguished from pool-local failures. Acceptance: Story 2, scenarios 3–5; Story 5, scenario 1; SC-003 and SC-005.
- **FR-022**: cardano-cli MUST provide an explicit device-backed KES-generation workflow by extending `node key-gen-KES` or adding a dedicated command, while preserving the existing software-generation command. It MUST identify the intended device and pool, generate the initial KES key on-device, produce a conventional verification-key file plus an encrypted signing-key export, and provide a documented supported path to a conventional signing-key file on the authorized backup/recovery system. Output descriptions MUST distinguish encrypted export from node-loadable plaintext; device errors MUST NOT trigger host generation. Exact new command names and flags are planning decisions. Acceptance: Story 1, scenarios 6–7; SC-007.
- **FR-023**: Before a pool's first device-backed generation, the supported recipient-setup workflow MUST create the backup recipient keypair on the authorized backup/recovery system and protect its private key with a confirmed non-empty passphrase. Only the public key MUST be enrolled on the device through management authorization. The passphrase and recipient private key MUST NOT be supplied to or stored on the primary or Pico; generation, evolution, signing, and scheduled activation MUST NOT require them. Acceptance: Story 1, scenarios 8–9.
- **FR-024**: The platform MUST provide a supported local recovery command that unlocks the protected recipient private key and writes a standard Cardano signing-key file only on the authorized backup/recovery system. It MUST authenticate the encrypted artifact and verify its expected device, pool, generation, and verification-key binding before publishing output. It MUST preserve the encrypted input, create output readable only by its owner, refuse existing output paths, and publish no partial plaintext on failure. Passphrases and secret key contents MUST NOT be echoed, logged, supplied through command-line arguments or environment variables, or written to incidental temporary files. Unlocked material MUST be released and cleared when the operation ends, without a persistent unlocked-key service. Acceptance: Story 1, scenario 10; SC-009.
- **FR-025**: The supported recipient-password-change workflow MUST operate locally on the authorized backup/recovery system, require unlocking the existing private key and confirmation of a non-empty replacement passphrase, and preserve the recipient keypair's identity. It MUST leave existing encrypted KES artifacts and device configuration unchanged and preserve a recoverable protected key if interrupted. Management-authorized recipient-key replacement MUST affect future generations only. Acceptance: Story 1, scenarios 11–12; SC-009.
- **FR-026**: Operator procedures MUST explain initial recipient setup and enrollment, passphrase custody, recovery, local password change, recipient-key replacement, archival of protected old recipient keys while their artifacts are needed, and irrecoverable-loss/compromise handling. They MUST recommend a long unique passphrase, protect private-key backups, and keep recovery credentials separately secured and off the primary. They MUST explain that a password change cannot revoke copied keys or previously exported plaintext; suspected KES-secret compromise requires fresh KES generation and certificate handling, not just a password change. Acceptance: Story 1, scenarios 8–12; SC-009.

### Key Entities *(include if feature involves data)*

- **Operator and Management Authority**: Operator manages deployment and external certificate/backup workflows. A separately held offline management authority approves sensitive enrollment, credential, recipient, deletion, and firmware-policy changes; it is not the pool cold key.
- **Device**: One Pico 2 with stable authenticated identity, protected durable state, device-wide health, and up to 32 independent pool registrations. It is a dedicated KES signer, not a general-purpose HSM.
- **Pool Registration**: Stable pool identity associated with its cold verification key, network identity and KES parameters, machine authorization, backup recipient, and replay/certificate history. Duplicate conflicting pool identities are rejected.
- **KES Generation**: A uniquely identified fresh keypair belonging to one pool, with public verification key, device-held evolving signing state, relative period, certificate association, and staged, certified, active, retired, expired, or unusable lifecycle state. Each pool has at most one active and one staged generation. Readiness is distinct from lifecycle state.
- **Certified Signing Context**: Pool and generation bound to a verified operational certificate, network parameters, absolute starting period, current relative period, and allowed lifetime. Absolute period is supplied by the node; relative period is measured from certificate start.
- **Encrypted Backup Artifact and Recipient**: Immutable generation-time initial-state backup bound to device, pool, generation, verification key, and approved recipient public key. The recipient keypair is created on the authorized backup/recovery system; its private key is stored there under passphrase protection and unlocked locally only for supported recovery or password maintenance. The Pico holds only the enrolled recipient public key. A password change preserves recipient identity and artifact compatibility; replacing the keypair changes future export recipients, not existing artifacts.
- **Node KES Source and Pool Authorization**: Explicit selection of file-based KES, kes-agent, or cardano-kes-forge for a credential, with an independently revocable pool machine identity for the device option. The kes-agent path remains a separate existing key-delivery option, not a device-signing protocol.
- **Activation Intent**: Durable operator-approved selection of a certified staged generation for activation when a node reports an eligible period; reconciled with committed device state after interruptions.
- **Signing Request and Result**: Intended pool, generation, exact content, period, and bounded request lifetime, paired with a verified signature or explicit failure; never a carrier for plaintext KES state.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: At least four of five representative operators, using the supplied instructions without developer assistance, generate a pool's certificate-ready public key and retrievable encrypted backup within 15 minutes on an already provisioned device, excluding external certificate issuance. They correctly identify that pool's active generation, backup availability, and remaining validity or stale-period warning within one minute.
- **SC-002**: A controlled-network exercise yields independently accepted blocks for 100 consecutive scheduled device-backed production opportunities across multiple pools on one host, spanning at least two period transitions and one hot rotation. No invalid signature is submitted and no plaintext KES key is supplied to the primary node. Disconnection and reconnection preserve node synchronization and restore subsequent accepted forging without changing the node process.
- **SC-003**: Single-pool warm signing completes within 100 milliseconds for at least 99% of 10,000 requests. Across 10,000 synchronized rounds of 32 admitted pool requests, every valid request completes within 500 milliseconds from admission to independently verified result, including queueing, required evolution or activation, and transport. Qualification covers all 32 active plus 32 staged generations, and separately background generation with one staged slot available, including aligned midpoint period transitions. Over-capacity requests fail explicitly within 500 milliseconds; authorized status completes within two seconds under saturation. These are acceptance targets, not prototype measurements.
- **SC-004**: The security acceptance matrix produces zero unauthorized signatures, cross-pool state changes, recipient redirections, or plaintext-secret disclosures on the primary across unauthorized-host, replay, management-impersonation, altered-backup, maintenance-access, firmware-replacement, and rollback attempts. Authorized encrypted export and separate recipient-side plaintext recovery succeed and are recorded distinctly, not misclassified as prohibited extraction.
- **SC-005**: At least 1,000 controlled ordinary-operation power interruptions, distributed across generation/backup publication, evolution, activation, credential changes, and deletion with all 32 pool registrations present, recover automatically to a consistent committed state without regressing acknowledged state or losing acknowledged artifacts. Cover all 32 active and staged generations and independently verify every returned signature. Separate intentional unrecoverable-corruption trials block only the affected scope and do not count as successful interruption recovery. Clean power-down/restart preserves all committed state and resumes authorized operation without manual unlock or regeneration; recovery time is recorded.
- **SC-006**: At least four of five representative operators prepare and approve a pool rotation within ten minutes once its replacement certificate is available. The rotation activates without node restart, including after an intervening restart of device or host-side service, and causes no signer-related missed opportunity for unaffected pools in the controlled workload. All five correctly identify the backup forward-security exception and the need to avoid simultaneous primary/backup forging.
- **SC-007**: All three node options independently produce accepted blocks in the controlled compatibility exercise. The unchanged software-generation command and the device-backed cardano-cli generation workflow both produce usable verification-key/signing-key pairs through their respective supported output/recovery paths. For a device generation, its recovered conventional key produces accepted backup blocks using the same externally cold-signed certificate during a separate, non-overlapping producer interval with the original device disconnected. Independent compatibility checks cover every Sum6KES relative period and applicable network lifetime boundaries, reject wrong-key/certificate inputs, and show ordinary evolution leaves the original backup and public key unchanged.
- **SC-008**: Before production deployment, preview and preprod each demonstrate at least two complete KES periods and ten independently observed accepted blocks, plus separate device-backed and conventional-backup intervals, one rotation, and disconnect/reconnect recovery. Full-capacity physical-device qualification and independent security review precede operator-approved mainnet use; software-only or prototype results do not satisfy these gates.
- **SC-009**: A complete recipient-lifecycle exercise successfully provisions a recipient, generates an encrypted KES export without supplying any recipient password/private key to the primary or device, recovers a matching conventional signing key on the authorized backup/recovery system, changes the recipient password without changing device configuration or artifact bytes, and recovers the same artifact again. Replacing the recipient makes a subsequent generation recoverable by the new key while the prior artifact remains recoverable by the old key. Every exercised wrong-password, wrong-recipient, altered-artifact, and existing-output case fails without publishing partial plaintext, overwriting existing keys, or exposing secrets in captured output. Interrupted password changes retain a usable protected recipient key. The resulting recovered KES file passes the conventional-backup acceptance in SC-007.

## Assumptions

- **Greenfield constraint**: New cardano-kes-forge firmware and host/operator components are implemented in Rust as required by the user. Do not copy, port, link, or depend on Pico HSM application code, its general HSM command surface, or its PIN/MKEK object model. The prototype supplies behavioral lessons and interoperability expectations, not an inherited implementation. Necessary changes inside the existing cardano-cli, cardano-node, and consensus projects follow those projects' native language and conventions; the Rust requirement is not a rewrite of those projects. Maintained cryptographic dependencies require review rather than being replaced with invented primitives.
- **Product boundary**: The platform covers device operation, operator management, cardano-cli generation/recovery integration, and the host-side integration needed by cardano-node. It is not a general-purpose HSM, wallet, transaction signer, on-chain pool-registration service, or custody system for cold or VRF signing keys. Multi-pool service on one primary host is in scope. Hosted multi-tenant management, remote fleet administration, and replacement of the operator's existing backup runtime or failover controller are not.
- **Local source checkouts**: The cardano-node source is located at `/home/westbam/haskell/cardano-node`; the cardano-cli source is located at `/home/westbam/haskell/cardano-cli`. Use these checkouts for integration research and planned changes to the respective projects.
- **Recipient-password lifecycle**: The password protects the recipient private-key file only on the authorized backup/recovery system; it is not a device PIN, KES-signing password, or secret shared with the primary. Set it during recipient setup before enrollment, change it locally without changing the keypair, and keep independently protected recovery copies and credentials off the primary. A password change does not revoke an old copied private-key file. Recipient-key replacement is a separate management-authorized operation for future exports; retain the old protected key and its credentials while old artifacts are needed. No password-reset bypass can recover a private key whose usable copies or unlocking credentials have all been lost.
- **Recovery tooling boundary**: Supply and document supported recipient setup, encrypted-KES recovery, and recipient-password-change commands as part of the platform's operator workflow. Planning selects exact command names and reviewed encrypted-file formats; it must demonstrate interoperability and secret-safe error handling rather than assume compatibility from an encryption algorithm name. The inspected `/home/westbam/haskell/scripts/cardano/mainnet/04c_genKESKeys.sh`, `01_protectKey.sh`, and `00_common.sh` provide workflow examples only. Their password-symmetric OpenPGP-in-JSON format and existing script commands are not adopted as the recovery contract: the selected design instead encrypts to the recipient public key and uses the password only to protect the recipient private key. No scripts from that checkout are a required runtime dependency.
- **Prototype-derived capacity and operation**: Adopt the prototype's target of 32 pools with one active and one staged generation each, unattended operation after one-time attended provisioning, independent pool credentials, and separate offline management authority. One device is a shared availability dependency, not redundant hardware. Performance and physical feasibility must be demonstrated for this new implementation, not inferred from the prototype.
- **Backup policy**: Adopt the prototype's encrypted generation-time export to a pre-enrolled recipient, with conventional file recovery only on the authorized backup/recovery system. There is no blanket export ban, but no plaintext device-export command, arbitrary current-state export, or device private-key import. A retained initial backup can derive later states and weakens pool-wide forward erasure; erasing or revoking device state does not erase that backup. Existing failover/failback procedures remain external and must prevent simultaneous forging.
- **Migration and recovery**: Move to device-generated keys at a normal KES rotation, not by importing an existing file key. The backup uses the same public key and certificate as its generation and evolves independently through conventional node behavior. A failed device may be replaced with fresh device generations and matching certificates while existing backup procedures maintain availability within their keys' validity. Loss of an artifact or its recipient private key cannot be undone by changing the recipient for future generations.
- **Period source**: cardano-node may provide period information and evolution instructions. The device is not a chain validator or trusted clock. It validates authorization, registered parameters, certificate binding, and monotonic lifetime bounds. An authorized compromised node can request permitted signatures, advance prematurely, or deny service; no guarantee of honest consensus behavior or non-equivocation is claimed. No evolution or wall-clock erasure occurs while unpowered.
- **Deployment and design decisions**: The exact transport, interaction surface, and internal design are planning decisions, not prescribed here. The prototype's C/Python implementation, HSM firmware profiles, wire opcodes, flash layout, and cryptographic-library choices are not requirements for the Rust project. New host/device protocol compatibility with the prototype is not required. Cardano file compatibility and preservation of both existing node KES options are required. Secure firmware acceptance is in scope; the prototype's particular remote-update mechanism and irreversible update-finalization replacement-risk exception are not adopted automatically.
- **Physical limits**: Protect against compromised-primary extraction and exposed-interface bypass; do not claim invasive chip-analysis, laboratory fault-injection, side-channel, or physical flash-substitution resistance. The board choice alone proves no security property. Planning must qualify suitable Pico 2 silicon and its protection capabilities before production, using the prototype's A4-or-later requirement as reference rather than accepting an unverified revision. Ordinary power interruption is a required recovery case, not an invasive-attack exclusion. If required security or capacity cannot be achieved, obtain an explicit requirement or hardware decision rather than silently weaken it.
- **Compatibility and qualification sources**: Behavioral reference: [prototype Sum6KES plan](../../../pico-hsm/CARDANO_SUM6KES_PLAN.md), especially multi-pool capacity, rotation-only backup, persistence, and third node-source sections. [Prototype qualification notes](../../../pico-hsm/doc/cardano-kes.md) record software/private-network exercises of device signing, conventional backup, and kes-agent, while explicitly stating that physical hardware and public-network qualification remain unverified. [Prototype operator runbook](../../../pico-hsm/deploy/kes/OPERATIONS) describes external certificate and backup boundaries. These sibling-repository references are research inputs, not build/runtime dependencies or reproduced results. Planning must pin and verify the supported Cardano release and authoritative Sum6KES behavior; prototype versions are reference baselines, not automatically adopted dependency pins.
- **Governance and evidence**: The project constitution remains authoritative. Implementation planning must consult the Software Observatory MCP, select applicable sensors, record limitations and coverage gaps, and define executable quality and performance gates before coding. This specification adopts product constraints and acceptance targets only; it does not claim that Rust firmware, node integration, backup recovery, hardware security, or performance has been implemented or verified. No new compliance certification or localization requirement is introduced.
