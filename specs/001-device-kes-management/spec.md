# Feature Specification: Device-Protected KES Management

**Feature Branch**: `001-device-kes-management`

**Created**: 2026-10-23

**Status**: Draft — Rust operator generation, unmodified Cardano CLI baseline, backup lifecycle, security modes, and mixed-source bulk credentials clarified

**Input**: Create cardano-kes-forge for secure KES generation, management, evolution, and signing on a Raspberry Pi Pico 2. Updated scope: a greenfield Rust project, not an HSM port; one device serves multiple pools on one machine; cardano-node gains a third configurable KES option while retaining file-based KES and single-pool kes-agent; bulk credentials may mix file-based KES and cardano-kes-forge only; device-generated keys support conventional backup producers; state survives power-down and the node may supply periods and evolution instructions.

## Clarifications

### Session 2026-10-23

- Q: What product scope supersedes the original single-pool, non-exportable-key specification? → A: The user supplied this clarification directly: build a greenfield Rust KES platform using the pico-hsm prototype as behavioral reference, without copying HSM code; share one device across multiple pools on the same host; add cardano-kes-forge as a third cardano-node KES option alongside unchanged file-based and kes-agent options; export compatible keys for backup block producers; perform evolution and signing on the device; preserve state across power-down and accept period/evolution information from cardano-node. No follow-up question was required. Prototype-derived defaults and their security tradeoffs are recorded under Assumptions.
- Q: How should operators request device-backed KES generation? → A: The earlier proposal to extend cardano-cli is superseded: use the Rust operator executable `kes-forge key-gen-KES` with the existing device-generation flags, without an era or `node` prefix, command alias, or host-generation fallback. The selected Pico 2 generates the initial KES key, exports its verification key for external cold-key operational-certificate issuance, and provides an encrypted export recoverable as the matching signing key for a conventional backup producer. Unmodified `cardano-cli-11.4.0.0`, commit `25f4d7a6b243d80ed7d716cc91b9c51d9265ace6`, remains required for certificate issuance, conventional key/query operations, and independent compatibility checks; no cardano-cli source modification or fork is required. Node/consensus modifications remain required. Retaining the initial backup key removes the deployment-wide forward-security guarantee even though the legacy node still evolves KES state for signing.
- Q: Where may the device-backed key-generation workflow write the plaintext `kes.skey` file? → A: Only on the authorized backup/recovery system (Option A). The user also requested investigation of password-protected export and the existing operator scripts before deciding how passwords are provisioned, protected, changed, and used for decryption.
- Q: Should the password protect a recipient private key on the backup system, or directly protect exports through a secret provisioned to the Pico? → A: Protect the recipient private key only on the authorized backup/recovery system (Option A). Enroll only its public key on the Pico. Generation needs no password; recovery unlocks the recipient private key locally. Changing its password does not change the recipient keypair, device configuration, or existing encrypted KES artifacts. Replacing the recipient keypair requires management authorization and affects future generations only.
- Q: How should development observability differ from release security? → A: The user supplied this clarification directly: development mode may leave the Pico 2 bootloader and debugging access unlocked and allow keys to be recovered for correctness checks; release mode must use the Pico 2 security features to protect system integrity and device-held keys. Development recovery is restricted to disposable test keys and explicit protected inspection outputs, not secret logging. Release requires verified hardware provisioning, excludes development extraction paths, and must not reuse keys exposed during development.
- Q: Must one node using `--bulk-credentials-file` support different KES sources for its individual pools? → A: Preserve bulk credentials and allow pools within the same bulk file and the same running cardano-node process to independently select cardano-kes-forge or file-based KES. KES-source exclusivity is per pool credential, not per process; supporting separate processes or homogeneous bulk files alone is insufficient. The subsequent single-pool kes-agent clarification narrows the supported bulk sources to these two.
- Q: Does bulk-credentials support need to include kes-agent? → A: No. The user clarified that kes-agent works only in single-pool mode. Preserve its existing single-pool support, but exclude it from bulk credentials; mixed bulk operation requires only cardano-kes-forge and file-based KES.
- Q: Must cardano-kes-forge support cardano-node's existing KES telemetry and logging? → A: Yes. Device-backed pools must retain the node's existing KES-period and remaining-key-lifetime telemetry and logs. Node integration derives these from host-known certificate/network information and confirmed device signing-state metadata, rather than requiring a separate device-only monitoring workflow.
- Q: Does the Pico need separate telemetry storage or expiry calculations? → A: No. Following source investigation, the user accepted host-side derivation: the certificate supplies the start period; network parameters determine the validity limit; node slot/time context determines network-period and calendar-time information. Existing forging telemetry also uses the key's confirmed relative evolution, which the device already persists for signing and recovery. The node reconciles that state through normal acknowledgements and status/recovery operations; a requested evolution is not proof of success. No telemetry-only device storage, countdown, expiry timestamp, or clock is required. Existing certificate/network bindings needed for secure signing remain unchanged.
- Q: Does routine KES rotation require multiple operators or special authorization beyond access to the primary node? → A: No. A single operator performs routine rotation using existing operational access to the primary block producer and its configured pool connection. Generating/staging a replacement and activating or scheduling it require no separate rotation credential, offline management approval, second operator, quorum, device PIN, or physical confirmation. Pool isolation and valid operational-certificate checks still apply; external cold-key certificate issuance and authorization for enrollment, credential/recipient changes, deletion, and firmware changes remain separate from routine rotation.

## User Scenarios & Testing *(mandatory)*

Stake-pool operators need one Pico 2 to protect the device-backed signing state of multiple pools on the same host, including pools loaded together by one cardano-node process through `--bulk-credentials-file`. Other pools in that same node may use file-based KES instead; kes-agent remains a single-pool option, not a bulk source. KES (key-evolving signatures) advances through numbered validity periods. Each pool has independent credentials, source selection, keys, certificates, and lifecycle state. The device performs evolution and signing for device-backed pools and does not transfer their signing keys into the node; file-based pools and separate single-pool kes-agent nodes retain their own existing key-handling behavior.

A controlled backup exception permits an encrypted copy of each newly generated initial signing state to be recovered as conventional Cardano key files on a separate authorized backup system. Device-local erasure and forward-only evolution do not erase exported backups or prevent those backups from deriving earlier or later signing states. An operational certificate authorizes a KES verification key for a pool and starting period; the existing external cold-key workflow continues to issue it.

**Security-mode scope**: Release mode is the default context for the secret-confinement and production-security requirements below. Development mode permits explicitly requested recovery of disposable device KES state on a trusted development machine, in addition to unlocked boot/debug access. This is a separate testing path, not the release backup workflow or normal node-signing interface. Correct cryptography, pool routing, period evolution, persistence, and failure handling remain required in both modes. Secrets remain prohibited in logs, diagnostics, fixtures, and version control in both modes; deliberate protected development recovery is not a logging feature.

### User Story 1 - Generate Pool Keys and Compatible Backups (Priority: P1)

An operator provisions the device, registers pools and their authorized backup recipients, then runs `kes-forge key-gen-KES` for each pool. The Pico 2 generates the initial KES key locally. The workflow supplies a standard public verification key for external certificate issuance through unmodified cardano-cli and an encrypted initial-state signing-key export; only the authorized backup/recovery system writes the decrypted conventional signing-key file.

**Why this priority**: On-device key creation must protect the primary host without preventing existing conventional backup producers from operating.

**Independent Test**: Exercise the unchanged software-generation command in unmodified `cardano-cli-11.4.0.0` and the device-only `kes-forge key-gen-KES` workflow for two registered pools. Obtain their public verification keys and encrypted signing-key exports, recover each export on the authorized backup/recovery system, and verify that the unmodified Cardano CLI baseline derives the matching public key and accepts the recovered signing-key file.

**Acceptance Scenarios**:

1. **Given** a provisioned device and an authorized pool registration, **When** a generation completes durably, **Then** it exposes a stable pool and generation identifier, standard `kes.vkey`, and one encrypted backup of the matching initial signing state; neither the primary host nor a node using cardano-kes-forge receives plaintext signing secrets.
2. **Given** an encrypted backup and its authorized recipient on a separate trusted system, **When** recovery completes, **Then** the resulting conventional `kes.skey` derives the supplied verification key and can be used with the same externally issued operational certificate as the device generation.
3. **Given** a retained generation-time artifact, **When** it is retrieved repeatedly or after evolution and restart, **Then** the same artifact is returned; ordinary evolution creates no fresh backup and changing the authorized recipient applies only to future generations.
4. **Given** a wrong recipient, altered artifact, unauthorized export request, or pool-mismatched credential in release mode, **When** access or recovery is attempted, **Then** it fails without revealing plaintext or changing protected state. Plaintext device export is unsupported in release mode; private-key import remains unsupported in both modes.
5. **Given** insufficient secure randomness, power loss, or a lost generation response, **When** the caller retries or inspects status, **Then** no incomplete generation is advertised as usable and an already committed generation is identified rather than silently replaced by a newly generated key.
6. **Given** existing use of `cardano-cli $era node key-gen-KES --verification-key-file /tmp/core.kes.vkey --signing-key-file /tmp/core.kes.skey`, **When** the operator runs that command with unmodified `cardano-cli-11.4.0.0`, **Then** existing software-generation behavior remains unchanged. When the operator instead runs `kes-forge key-gen-KES` with the existing device-generation flags and no era or `node` prefix, the initial key is generated only on the selected Pico 2 for the intended pool; no old device-generation command alias is provided and failure never silently falls back to host generation.
7. **Given** a device-generated verification key and encrypted signing-key export, **When** the operator completes the documented recovery workflow on the authorized backup/recovery system, **Then** it writes a conventional `kes.skey` matching `kes.vkey`. The verification key is available for external cold-key certificate issuance without backup decryption; an encrypted artifact alone is not described as a file that an unmodified backup node can load.
8. **Given** an authorized backup/recovery system, **When** the operator sets up a backup recipient before first device-backed generation, **Then** the supported workflow creates a recipient keypair there, protects its private key with a confirmed non-empty passphrase, and makes only its public key available for management-authorized pool enrollment. Neither the primary nor the Pico receives the recipient private key or passphrase.
9. **Given** an enrolled recipient public key and an unattended primary, **When** a new KES generation is requested, **Then** the device produces the encrypted signing-key export without a password prompt or access to the recipient private key.
10. **Given** an encrypted KES export, the protected recipient private key, and the correct passphrase on the authorized backup/recovery system, **When** the supported recovery command runs, **Then** it verifies the artifact's integrity, expected device/pool/generation, and matching verification key before publishing a restricted-permission conventional `kes.skey`. It does not print secrets or modify the encrypted input. A wrong password, wrong key, altered artifact, or existing output path produces an explicit failure without publishing partial plaintext or overwriting an existing key.
11. **Given** a usable protected recipient private key, **When** its password is changed through the supported local workflow, **Then** the keypair identity remains unchanged and existing artifacts can still be recovered with the newly protected private-key file, with no device update. An interrupted password change preserves a usable old or new protected file rather than destroying the only recoverable key.
12. **Given** a management-authorized replacement recipient keypair, **When** it is enrolled, **Then** future KES generations are encrypted to the new recipient while old artifacts still require the old recipient private key. Losing all usable copies of that key or its unlocking credentials makes those artifacts unrecoverable; changing a password or recipient does not revoke copied secrets.
13. **Given** an explicitly selected development device containing only disposable test keys, **When** a developer uses boot/debug access or requests controlled recovery of a selected pool's current KES state, **Then** the state can be inspected on the trusted development machine and independently checked against that generation's public key and period. The output is explicitly development-only, restricted to the requesting developer, and excluded from logs and version control; inspection does not require retaining already-erased states.
14. **Given** a fully provisioned release device, **When** a caller attempts the same development-key recovery, debug read, or unrestricted bootloader access, **Then** the attempt exposes no plaintext key or protected state. Management authority does not enable a hidden development bypass, while the approved recipient-encrypted backup workflow continues to work.
15. **Given** release firmware on an unlocked or incompletely provisioned board, **When** readiness is checked or production key generation/signing is requested, **Then** the system reports that release security is not established and refuses those operations. Merely compiling a release build or changing a host flag is not proof of lockdown.
16. **Given** hardware previously used in development, **When** the operator prepares it for release use, **Then** development keys and potentially exposed trust material are discarded, fresh release trust material is provisioned, required hardware protections are applied and verified, and fresh release KES keys are generated only after the protected boundary is established. If exposed trust material cannot be securely replaced, that hardware is not eligible for release use.
17. **Given** a release-provisioned device, **When** a caller changes configuration, requests a development mode, or attempts to load unsigned, unauthorized, development, or prohibited older firmware, **Then** the device does not expose its release state or become an unlocked development signer.

### User Story 2 - Select Device Signing for Multiple Pools (Priority: P1)

An operator configures one cardano-node process with `--bulk-credentials-file`, selecting file-based KES or cardano-kes-forge independently for each pool entry. Both sources can operate concurrently within the same bulk file and node process. Device-backed entries share one Pico 2 and route requests only to their own authorized device state; file-based entries need no device registration. Individual non-bulk startup retains all three options, including existing single-pool kes-agent support.

**Why this priority**: Operators must be able to adopt device-backed signing pool by pool without splitting an existing bulk-configured node into separate processes, converting every pool, or breaking legacy credentials.

**Independent Test**: Start one actual cardano-node process from a single bulk credentials file with at least two distinct pools: one file-based and one cardano-kes-forge. Independently validate blocks from every pool, disconnect/reconnect the device while the file-based pool continues, and verify correct pool/certificate routing across evolution and device-key rotation. Separately exercise unchanged legacy bulk files and individual startup for all three sources, including single-pool kes-agent, plus the conventional recovered-key backup workflow. Verify that selecting kes-agent for a bulk entry is rejected rather than silently changing sources.

**Acceptance Scenarios**:

1. **Given** a valid individual credential selecting one of the three KES sources, or a mixed `--bulk-credentials-file` selecting exactly one of file-based KES and cardano-kes-forge per pool entry, **When** the node starts, **Then** each pool uses its own selected source. Both supported bulk sources operate within the same process; source exclusivity does not apply globally across that process. Existing supported legacy bulk files and individual file-based/kes-agent configurations retain their behavior; kes-agent remains single-pool only.
2. **Given** multiple authorized device-backed pools sharing the Pico 2, including entries within one bulk-configured node, **When** their signing attempts occur concurrently, **Then** every successful result matches the correct pool, generation, certificate, exact signing content, and period and is independently verified before block submission. No device-backed pool's plaintext KES state is transferred to the node; legacy-source pools retain their own existing key-handling behavior.
3. **Given** a credential for one pool, malformed input, a wrong certificate or network, or a stale generation, **When** signing or evolution targets another pool or mismatched context, **Then** the request fails without changing another pool's state or submitting an invalid block.
4. **Given** a mixed bulk-configured node and device absence at startup or disconnection during operation, **When** a device-backed pool needs to sign, **Then** that attempt fails explicitly while synchronization and eligible file-based pools continue. Reconnection restores later valid device-backed signing without node restart, manual runtime unlocking, or automatic switching of any pool's KES source.
5. **Given** excessive requests or a pool-local fault, **When** healthy pools continue requesting service, **Then** excess work receives bounded failures and one pool does not monopolize the device or select another pool's key. A device-wide hardware failure may affect every attached pool and is reported as such.
6. **Given** an exported conventional key and its certificate, **When** the operator stops the primary producer and starts the backup through the existing file-based option, **Then** independent validation accepts its blocks without requiring cardano-kes-forge on the backup. Failover scheduling and prevention of simultaneous primary/backup forging remain the operator's responsibility.
7. **Given** a development device or missing/mismatched hardware-security evidence, **When** normal production node/host integration connects, **Then** it rejects the device for production signing. A separately explicit development opt-in permits isolated test operation, clearly labels the mode, and does not override release-device locks or change the behavior of the existing file-based and kes-agent options.
8. **Given** a legacy bulk credentials file containing only supported file-based entries, **When** it is loaded by the updated node, **Then** it works unchanged without requiring device configuration, device hardware, or a running kes-agent. In a mixed file, unchanged legacy entries remain usable alongside entries selecting cardano-kes-forge.
9. **Given** a bulk entry with conflicting KES-source selections, an unsupported bulk source such as kes-agent, missing required source configuration, or a conflicting duplicate pool identity, **When** startup configuration is validated, **Then** the bulk configuration is rejected with an error identifying the offending entry and reason without exposing secrets. A recognizable legacy entry retains its existing file-based meaning; no malformed new entry inherits another pool's source, credentials, or signing context.
10. **Given** one running node with file-based KES and cardano-kes-forge selected for distinct bulk pools, **When** a device-backed pool advances or rotates its generation, or the device becomes unavailable, **Then** each other pool retains its own source, certificate, and evolution state. Device unavailability affects only device-dependent pools; shared-process execution does not authorize cross-pool signing or fallback.

### User Story 3 - Resume and Evolve Safely after Power-Down (Priority: P1)

An operator powers down or disconnects the device and later resumes service without regenerating keys, importing a backup, or losing committed pool state. Each node supplies its current period or evolution request, and the device catches up safely before signing.

**Why this priority**: Durable state and unattended resumption are necessary for both KES correctness and ordinary operation; routine power loss must not be treated as a reason to abandon a valid key.

**Independent Test**: Populate multiple pools with independent periods and staged generations, power-cycle the device, reconnect their nodes, advance across skipped periods, and verify signatures and retained public metadata. Interrupt lifecycle operations at their persistence boundaries.

**Acceptance Scenarios**:

1. **Given** successfully committed pool registrations, authorizations, generations, certificates, backup artifacts, and periods, **When** the device is powered off and on, **Then** those records remain available and authorized service resumes unattended after safe recovery, without creating new identities or resetting periods.
2. **Given** a node-supplied later period within a generation's valid lifetime, **When** evolution is requested, **Then** the device performs and durably commits forward evolution before signing in that period. The public verification key, generation identifier, certificate, and generation-time backup stay unchanged.
3. **Given** a repeated current-period request or an earlier period, **When** it is processed, **Then** the current-period request does not advance again and the earlier-period request is rejected, including after reboot. Ordinary signing does not itself create a new generation or require a persistent lifecycle mutation.
4. **Given** power loss during an ordinary state-changing operation within supported storage behavior, **When** recovery runs, **Then** it automatically recovers a consistent committed state, never earlier than the last acknowledged state, and finishes required obsolete-state cleanup before serving. A durable but unacknowledged successor is reconciled rather than repeated. Irrecoverable corruption is separately reported and blocks the affected state; it is not silently reinitialized or counted as successful power-loss recovery.
5. **Given** a device left unpowered across several periods, **When** a node reconnects with the current period, **Then** the device catches up before signing if the generation is still valid, or explicitly expires it and awaits an authorized replacement. It makes no claim to evolve or erase secrets while unpowered.
6. **Given** concurrent generation, evolution, activation, or delayed responses for the same pool, **When** operations complete, **Then** none restores an older period, resurrects a retired device generation, overwrites newer committed state, or associates a response with a different request.

### User Story 4 - Inspect and Rotate Pools Independently (Priority: P2)

A single operator with existing operational access to the primary block producer monitors each pool through cardano-node's existing KES telemetry and logs as well as device status, generates a replacement and matching backup, obtains a certificate through the existing external workflow, and activates or schedules the replacement without stopping other pools or restarting their nodes. Routine rotation uses the primary's configured pool connection without a separate authorization or approval step. Choosing device-backed signing must not remove the existing visibility of KES periods and remaining key lifetime.

**Why this priority**: Multi-pool operation is useful only if normal replacement and management do not disrupt unrelated block production.

**Independent Test**: Begin with all supported pool registrations already provisioned. Have one operator use existing primary-node access and configured pool connections, without an offline management credential or additional rotation authorization, to generate and retain active and staged generations, rotate one pool while others sign, and schedule an activation that executes after restarting the device and host-side service. Supply replacement certificates through the existing external cold-key workflow. Capture the node's existing KES metrics and logs for single-pool device operation and mixed file/device bulk operation, compare outputs with the conventional source for equivalent certificate, network/time, and confirmed key-evolution contexts, and exercise expiry, failed evolution, lost acknowledgements, disconnection, and recovery without exposing signing keys. Derive certificate expiry and time estimates on the host without requiring a device telemetry store or clock.

**Acceptance Scenarios**:

1. **Given** a provisioned device, **When** an operator requests status, **Then** it reports device health and per-pool identity, authorization, active and staged generations, certificate start, current relative period, remaining validity, backup availability, and signing-blocking conditions without exposing secrets. Remaining-validity information identifies stale or missing node-period observations rather than claiming current readiness.
2. **Given** an active pool and one operator with existing primary-node access, **When** the operator generates and stages a replacement through that pool's configured connection, **Then** its public key and encrypted backup are available before certificate issuance while that pool and the others remain able to sign, without separate management approval or rotation credentials. A second staged generation conflicts rather than silently replacing the first; the enrolled backup recipient remains unchanged.
3. **Given** a staged generation, **When** a certificate for another pool, key, network context, or unacceptable certificate counter is supplied, **Then** certification or activation fails without replacing a valid active generation. Certificate issuance and cold secrets remain outside this platform.
4. **Given** a valid certified staged generation and one operator with existing primary-node access, **When** the operator activates it through the configured pool connection at an eligible node-supplied period, **Then** the device commits the replacement, removes its superseded active secret, and subsequent signing uses the matching new certificate without node restart or additional approval, credential, device PIN, or physical confirmation. A raced old-generation request completes before activation or fails explicitly; it cannot mix old and new signing contexts.
5. **Given** a future activation scheduled by that operator through existing primary-node access, **When** the node later reports an eligible period, **Then** activation proceeds without another human action or authorization step. Restarting device, node, or host-side service preserves or reconciles that intent and the committed public certificate; device state is not rolled back to match a stale host file.
6. **Given** an expired active generation with no ready replacement, **When** signing is requested, **Then** it fails explicitly rather than generating a new key or certificate automatically. A later valid certified replacement can restore service.
7. **Given** a device-backed pool with a known active certificate, network parameters, node slot/time context, and confirmed relative key evolution, **When** the node emits its existing KES telemetry and logs, **Then** node integration derives certificate validity and time estimates from public host context and populates key-state fields from confirmed evolution. The existing forging current-period value is certificate start plus confirmed relative evolution, not an unconfirmed target or independently advancing network period. Outputs retain conventional meanings, names, units, emission conditions, and warning behavior for equivalent contexts, without a replacement dashboard or telemetry-only device storage.
8. **Given** single-pool operation or a mixed bulk node whose pools have different certificate start periods and active generations, **When** a period boundary, hot rotation, or expiry occurs, **Then** subsequent normal KES telemetry/log emissions reflect the correct active context under the node's existing identity and aggregation conventions. A staged key does not replace the active key's remaining lifetime, and a delayed report for a retired generation cannot overwrite current information.
9. **Given** device disconnection, restart, failed evolution, a lost acknowledgement, or stale/missing device observations, **When** KES information is reported, **Then** the node does not treat a requested period as confirmed device evolution or infer signing readiness from certificate validity. Public certificate validity and time estimates remain derivable from host-known metadata and node context without a live device response. Unknown device state is reported through the existing error/unavailable conventions, including defined sentinel values rather than fabricated successful measurements. Reconnection reconciles active generation and committed evolution before normal key-state reporting resumes; it exposes no secrets and does not disrupt healthy file-based pools.

### User Story 5 - Revoke Pool Access and Recover Service (Priority: P2)

An operator replaces or revokes a pool's machine credential, deletes a pool, or retires the device through a separate management authority. Existing exported keys support backup producers if the device fails; replacement hardware receives newly generated keys rather than imported historical state.

**Why this priority**: Pool isolation and recovery must remain meaningful despite the intentional backup exception and shared hardware.

**Independent Test**: Revoke one pool's credential while another signs, restart the device, attempt replay and cross-pool operations, and retire a test registration. Rehearse an operator-managed backup interval and replacement-device provisioning.

**Acceptance Scenarios**:

1. **Given** a registered pool, **When** management-authorized credential replacement or revocation commits, **Then** the old credential cannot access that pool after restart, while unrelated pools remain available.
2. **Given** a normal pool machine credential, **When** it attempts to enroll or delete pools, replace credentials, redirect future backups, or authorize firmware changes without management approval, **Then** the device rejects it. Replayed or altered management authorizations also fail without changing state.
3. **Given** an explicitly management-authorized pool deletion or device retirement, **When** success is reported, **Then** the affected device-held secrets and authorizations stay unusable after restart. The operation does not claim to erase previously exported artifacts or remotely invalidate existing backup producers.
4. **Given** a failed or lost device, **When** the operator uses an available generation-time backup through the existing procedure, **Then** a conventional producer can operate for that key's remaining valid lifetime without the original device. The procedure requires avoiding concurrent forging and explains that unreachable devices and external copies cannot be remotely erased.
5. **Given** replacement hardware, **When** the operator restores the device-backed service, **Then** it generates fresh keys and uses new matching certificates through the normal external workflow; there is no device private-key import or rollback recovery path. Missing backup artifacts or recipient keys are explicit limits, not recoverable through a hidden bypass.

### Edge Cases

- All 32 pools have active and staged generations; a 33rd registration or second staged generation is rejected without overwrite. Sparse registrations retain their stable identities, and deletion/re-enrollment does not silently reset replay or certificate history.
- Multiple pools reach a KES boundary simultaneously, including the Sum6KES midpoint transition. Generating or rotating one pool must not starve others or undo evolution committed during background work.
- The node requests an earlier period, repeats the current period, skips periods, supplies an inconsistent network context, or reaches the first invalid period. KES periods are not epochs or a hardcoded number of days.
- Power fails during generation, backup publication, evolution, activation, credential changes, or deletion. No partial artifact/key pair is advertised as complete, and acknowledged state never regresses.
- A response is lost after a durable change, a request is duplicated, or a late result arrives after cancellation. Status reconciliation identifies the committed result without creating another generation or accepting a stale signature.
- A backup is altered, addressed to the wrong recipient, lost, or retrieved after its generation is no longer retained. Retrieval of a retained artifact is repeatable; operators must archive it before rotation reclaims it. Recipient changes do not rewrite existing backups.
- A recipient password change is interrupted, a wrong password is entered, or the recovery output path already exists. Preserve a recoverable protected recipient key, fail without partial plaintext output, and never expose secrets in diagnostics.
- The operator changes the password protecting a recipient private key but retains the same keypair. Existing KES artifacts and device enrollment remain unchanged. A copied old protected private-key file is still unlockable with its old password; password changes are not revocation.
- Primary and backup use the same key and certificate. Their evolution is independent; no ordinary evolution export or continuous secret synchronization is needed. Shared certificates do not prevent double forging.
- A compromised authorized primary can request signatures, advance its authorized pools prematurely, generate staged replacements, activate replacements for which valid matching certificates are available, or deny service. Routine rotation has no additional approval boundary beyond existing primary access; this does not permit forging a cold-key certificate. In release mode the primary must not extract plaintext keys, redirect backup recipients without management authority, or bypass firmware and storage protections. Development mode makes no such extraction-resistance claim and must never hold production secrets. Pool isolation does not protect credentials already stolen from the same host.
- A pool-local damaged record blocks that pool rather than selecting another pool's state. Device-wide configuration damage, entropy failure, or hardware loss may block all pools and must be reported distinctly.
- File-based or kes-agent mode remains explicitly selectable for single-pool startup; bulk startup supports file-based KES and cardano-kes-forge only. Failure of a configured cardano-kes-forge source never silently selects another source as a fallback.
- A single bulk file mixes legacy file-based entries with explicit cardano-kes-forge entries. Source selection must remain per entry; list ordering, a shared node process, or another pool's configuration must not redirect signing.
- A mixed bulk entry is malformed, selects more than one source, requests kes-agent, or duplicates a pool identity with conflicting credentials. Reject unsupported bulk sources explicitly. Distinguish static configuration rejection from later runtime device unavailability; a valid file-based pool must not acquire a dependency on the device used by another pool.
- Development and release firmware, host settings, and actual hardware protection states disagree. Report the mismatch and refuse release readiness; do not silently treat a development device as secure because a build or configuration label says release.
- Provisioning is interrupted or a required irreversible hardware lock cannot be verified. Keep production key creation/signing blocked; never apply irreversible security configuration implicitly during ordinary development builds, flashing, or startup.
- A development key or trust secret has been inspected or copied before a release transition. Locking the board cannot make that copy secret again; discard it and use fresh release material, or replace hardware that cannot establish a fresh protected trust boundary.
- KES telemetry crosses a certificate start, a period boundary, the last valid period, or expiry. Preserve existing node units, validity-boundary conventions, and warning behavior; do not confuse the current network period with the device's last committed relative evolution period or use a hardcoded wall-clock KES duration.
- A staged replacement, delayed status response, or device outage races with rotation and monitoring. Keep observations bound to their pool and generation, preserve existing bulk aggregation semantics, distinguish cached public validity from confirmed device readiness, and never let an old generation reset the active key's reported lifetime.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: One Pico 2 MUST serve up to 32 independent registered device-backed pools concurrently on one primary machine, including 32 active and 32 staged generations at once. These pools MUST be supportable within a single bulk-configured node as well as across node processes. ### Key Entities *(include if feature involves data)*

- **Operator and Management Authority**: A single operator performs routine KES rotation using existing operational access to the primary node and its configured pool connection; there is no separate rotation approval role. The operator also manages deployment and external certificate/backup workflows. A separately held offline management authority governs enrollment, credential, recipient, deletion, and firmware-policy changes, not routine rotation; it is not the pool cold key. These are distinct authorities, not a requirement for different people.
- **Device**: One Pico 2 with stable authenticated identity, durable state, device-wide health, and up to 32 independent pool registrations. Security identity includes the declared firmware mode, observed hardware-protection state, and whether release readiness is verified. Development devices are explicitly non-production and permit controlled test-state inspection; release devices enforce the protected boundary. It is a dedicated KES signer, not a general-purpose HSM.
- **Pool Registration**: Stable pool identity associated with its cold verification key, network identity and KES parameters, machine authorization, backup recipient, and replay/certificate history. Duplicate conflicting pool identities are rejected.
- **KES Generation**: A uniquely identified fresh keypair belonging to one pool, with public verification key, device-held evolving signing state, relative period, certificate association, and staged, certified, active, retired, expired, or unusable lifecycle state. Each pool has at most one active and one staged generation. Readiness is distinct from lifecycle state.
- **Certified Signing Context**: Pool and generation bound to a verified operational certificate, network parameters, absolute starting period, current relative period, and allowed lifetime. Absolute period is supplied by the node; relative period is measured from certificate start.
- **KES Monitoring Context**: Host-side association of pool/generation, operational certificate, network lifetime parameters, node slot/time context, and last confirmed device signing state with freshness/availability. Certificate start comes from the certificate; expiry period additionally needs network lifetime parameters; calendar-time estimates need node time/era context. Existing forging current-period information uses certificate start plus confirmed relative key evolution, which is distinct from the current network period. Device observations reuse metadata already needed for secure signing and recovery, not a separate telemetry store; existing node aggregation preserves the underlying pool association.
- **Encrypted Backup Artifact and Recipient**: Immutable generation-time initial-state backup bound to device, pool, generation, verification key, and approved recipient public key. The recipient keypair is created on the authorized backup/recovery system; its private key is stored there under passphrase protection and unlocked locally only for supported recovery or password maintenance. The Pico holds only the enrolled recipient public key. A password change preserves recipient identity and artifact compatibility; replacing the keypair changes future export recipients, not existing artifacts.
- **Development Inspection Output**: Explicitly requested recovery of disposable current KES state, associated with its development device, pool, generation, and period. It is accessible only in the trusted development environment, is not a release backup artifact or ordinary diagnostic, and must never be reused as release secret material.
- **Node KES Source and Pool Authorization**: Exactly one source per pool: individual single-pool startup selects file-based KES, kes-agent, or cardano-kes-forge; an entry in `--bulk-credentials-file` selects only file-based KES or cardano-kes-forge. One bulk-configured node process can own entries using both supported sources concurrently. Each entry binds its own source configuration, certificate, and credentials; device-backed entries additionally have an independently revocable device-pool machine identity. The kes-agent path remains a separate existing single-pool key-delivery option, not a bulk source or device-signing protocol.
- **Activation Intent**: Durable selection of a certified staged generation and activation period, scheduled by the single operator through existing primary-node access and the configured pool connection. It is reconciled with committed device state after interruptions and executes when a node reports an eligible period, without a separate approval record or further authorization step.
- **Signing Request and Result**: Intended pool, generation, exact content, period, and bounded request lifetime, paired with a verified signature or explicit failure; never a carrier for plaintext KES state.

No scripts from that checkout are a required runtime dependency.
- **Prototype-derived capacity and operation**: Adopt the prototype's target of 32 pools with one active and one staged generation each, unattended operation after one-time attended provisioning, independent pool credentials, and separate offline management authority. One device is a shared availability dependency, not redundant hardware. Performance and physical feasibility must be demonstrated for this new implementation, not inferred from the prototype.
- **Routine rotation authority**: FR-004 defines the authorization boundary; FR-013 defines rotation behavior. Configured per-pool authentication is transparent to the operator. External cold-key certificate issuance remains a separate workflow: primary access neither grants certificate-issuance authority nor replaces a valid matching certificate.
- **Bulk deployment and capacity**: A single node serving several pools through `--bulk-credentials-file` is a required deployment, not merely several node processes on one machine. Bulk mode supports per-pool selection between file-based KES and cardano-kes-forge only; kes-agent works only in single-pool mode and extending it to bulk mode is out of scope. The device's 32-pool capacity counts only pools selecting cardano-kes-forge; it is not a new limit on file-based pools or separate single-pool kes-agent nodes. Selection is established through startup credentials; this clarification does not require live reconfiguration of a pool's KES source. Planning must define the backward-compatible bulk-file representation for the two supported sources.
- **Backup policy**: In release mode, use the prototype's encrypted generation-time export to a pre-enrolled recipient, with conventional file recovery only on the authorized backup/recovery system. There is no plaintext release-device export, arbitrary release current-state export, or private-key import. Explicit development-only recovery of disposable current state is allowed under FR-028 and does not modify the release backup contract. A retained initial backup can derive later states and weakens pool-wide forward erasure; erasing or revoking device state does not erase that backup. Existing failover/failback procedures remain external and must prevent simultaneous forging.
- **Migration and recovery**: Move to device-generated keys at a normal KES rotation, not by importing an existing file key. The backup uses the same public key and certificate as its generation and evolves independently through conventional node behavior. A failed device may be replaced with fresh device generations and matching certificates while existing backup procedures maintain availability within their keys' validity. Loss of an artifact or its recipient private key cannot be undone by changing the recipient for future generations.
- **Period source**: cardano-node may provide period information and evolution instructions. The device is not a chain validator or trusted clock. It validates authorization, registered parameters, certificate binding, and monotonic lifetime bounds. An authorized compromised node can request permitted signatures, advance prematurely, or deny service; no guarantee of honest consensus behavior or non-equivocation is claimed. No evolution or wall-clock erasure occurs while unpowered.
- **Existing KES monitoring contract**: Node integration owns telemetry derivation. Source investigation found that the CLI certificate-lifetime query uses the operational certificate, network parameters, chain slot, and era/time information without a KES signing key. The node's existing forging telemetry instead derives its current key period from certificate start plus confirmed key evolution, and its remaining periods from that state and certificate expiry. Planning must preserve this distinction and inventory the supported release's fields, logs, warning conditions, error sentinel values, emission cadence, and bulk identity/aggregation conventions in the recorded checkouts. Reuse ordinary device acknowledgements and recovery/status reconciliation for committed signing-state metadata; do not add telemetry-only device persistence, a countdown, an expiry timestamp, or a clock. This does not remove device certificate/network bindings required for signing security or change existing monitoring into a broader telemetry redesign.
- **Deployment and design decisions**: The exact transport, interaction surface, and internal design are planning decisions, not prescribed here. The prototype's C/Python implementation, HSM firmware profiles, wire opcodes, flash layout, and cryptographic-library choices are not requirements for the Rust project. New host/device protocol compatibility with the prototype is not required. Cardano file compatibility and preservation of both existing node KES options are required. Secure firmware acceptance is in scope; the prototype's particular remote-update mechanism and irreversible update-finalization replacement-risk exception are not adopted automatically.
- **Development and release boundary**: Development mode is for disposable test keys in an isolated trusted development environment; unlocked boot/debug access is intentional and provides no production confidentiality or firmware-integrity guarantee. Release mode requires an approved, verified hardware security configuration, not merely compiler optimization or a firmware label. Correctness behavior remains shared; only the explicitly identified inspection and hardware-protection differences are permitted. No production secrets are used in development, and exposed development material is never promoted to release. These defaults preserve the constitution's ban on secret logging without prohibiting deliberate protected test-key recovery.
- **Meaning of all security features**: Use all security capabilities applicable to the supported Pico 2 silicon and the stated integrity/key-protection threat model. Planning selects exact hardware settings and documents any genuinely inapplicable or incompatible capability; it must not blindly enable every irreversible setting or introduce unsafe recovery backdoors. Inability to satisfy an applicable required protection requires an explicit requirement/hardware decision, not a silently weakened release. No hardware-security capability is claimed proven by this specification.
- **Physical limits**: Release mode must protect against compromised-primary extraction and exposed-interface bypass; development mode intentionally permits inspection and has no equivalent extraction-resistance claim. Do not claim invasive chip-analysis, laboratory fault-injection, side-channel, or physical flash-substitution resistance. The board choice alone proves no security property. Planning must qualify suitable Pico 2 silicon and its protection capabilities before production, using the prototype's A4-or-later requirement as reference rather than accepting an unverified revision. Ordinary power interruption is a required recovery case, not an invasive-attack exclusion. If required security or capacity cannot be achieved, obtain an explicit requirement or hardware decision rather than silently weaken it.
